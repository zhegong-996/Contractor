# 01 · 产品与业务架构

> 详细定稿见 `docs/ARCHITECTURE-v0.6.md`（设计，不等于全部实现）、`docs/PRD-v0.6.md`；现状口径见 `docs/SYSTEM-ARCHITECTURE.md` 与 `docs/ADAPTATION-v0.6.md` 最新边界声明。

## 1. 一句话定位

小规模、高信任、以知识与软件产出为主的团队：需求从 IM 发起，按用途授权专业资料、连续交接，成果交付到本机 Git 或专业知识空间，**由人验收**。现有底座像「很靠谱的工单系统」，v0.6 要补的是「一个组织」——除了「这单跑完没有」，还要回答 **谁对什么负责、凭什么算做对了、AI 依据什么做的**。

## 2. 渠道分工（产品形态约束）

- **飞书 IM**：发起任务、追问、通知回写、最终核可。用户用中文自然语言指令（`src/user-language.ts`）。
- **工作台**：授权、留痕、审阅、签字。**工作台不是第二个发起入口**。
- **前端形态**：Paperclip 插件式单页，侧栏 `/SUI/knowledge-workspaces`，**5 个 view tab，无前端路由库**。移除 Plugin SDK 与这条约束冲突，见 `08-OPEN-DECISIONS.md`。

## 3. 角色（口径不能混）

| 角色 | 管什么 | 不可下放 |
|---|---|---|
| 组织级 owner | 职能注册表、转移授权策略 | 职能 ID 稳定性、责任链 |
| Workspace owner（数据归属方） | 验证等级、跨空间授权审批 | 系统安全底线、高风险签字 |
| 职能 owner | 起草验收标准、联签、兜底责任 | 标准不得由承接人自定 |
| 发起人 / 承接人 | 设目标与边界 / 执行（能力依据须来自真实 Task 产出） | 验收在原会话由发起人做 |
| 独立评审者 | 逐项判定，须支持截图等视觉输入 | 不得是产出模型 |
| 资料负责人 | 某条知识的采用与撤回 | 私有资料不得自动进共享 Wiki |

## 4. 端到端闭环（8 步，4 个人工决策点）

`发起 → 定职能责任* → 跨空间授权* → 开工前锁定验收清单* → 执行与交接 → 独立逐项评审 → 代码交付/知识沉淀 → 原发起人在原会话确认验收*`

`*` 为人工决策点。**报告、模型判定、CI 通过、合并审批都不替代最后一步**；SUI-129 至今未核可。

## 6. 功能成熟度三档（决定「能不能对外说已支持」）

**已跑通且有回归证据**：中文指令 7 条、派单/交接、限时授权、Context Pack 裁剪、知识候选→采用/撤回、开工前锁定清单 + 逐项报告 + Trace、本机 Git 交付全链（含自动合并与预览发布）、组织映射 3 人导入、国内服务实时探测、统一路由 Trace、B1 共享记忆主干与四类投影、11 步真实浏览器走查。

**预备配置 / 不等于启用**：模型三档策略（不存 Key）、L2 组织图草稿（人审后生效）、飞书部门 scope 授权命令（需本人在飞书确认）、Cognee 原生 LLM/embedding/cognify 链路（代码已实现、允许外部模型 API，但**缺端点与凭据，真实调用未发生**）。

**未接通 / 未发生**：企业微信 / 腾讯文档 / 钉钉 / 国内代码托管 / 公有云 CI / 海外 SaaS（按约定**没有可点入口**）、全员 SSO 与真实员工入驻、生产发布、真人在真实业务单「确认验收」、C（三层 Router 与平台底座切换）。

## 7. 五条业务红线

1. `Agent 完成 ≠ 业务验收`；最终核可只能由原发起人在原会话做。
2. 高风险动作（授权审批、知识采用、正式跨职能派单、发布）必须真人签字。
3. 私有资料不得自动进共享 Wiki；检索时按当前身份重评权限。
4. 验收标准在开工前锁定，不得由承接人自定。
5. 独立评审者不得是产出模型；证据必须可回溯到 L1 原文。
