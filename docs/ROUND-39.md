## 1. 事件源与 GitHub 合并

### 1.1 少一个必开开关

`eventInbox.enabled` 缺省从 `false` 改为 `true`。这不是放松安全，而是**去掉一个只会被忘记的开关**：

- 没有 `sources` 就没有入口 —— 任何 `POST /events/:source` 都回 `source-not-configured`；
- 登记了来源但没有密钥 —— 回 `secret-not-configured`，不提供裸奔模式；
- 显式写 `enabled: false` 仍然全拒（`events-disabled`）。

测试里把这个语义钉住了：默认配置 + 空 sources → `source-not-configured`；显式关闭 + 有来源 + 有密钥 → 仍然 `events-disabled`。

### 1.2 一个来源只有一条路径

此前 GitHub 有两条互不相干的入口：`/github/webhook`（收到就建单）与 `/events/:source`（进收件箱等规则）。同时开就是同一事件建两单。

现在由 `eventInbox.claims('github')` 判定：

```text
POST /github/webhook
  ├─ 已登记 github 来源 → 交收件箱（202），由 when 规则决定开不开单
  └─ 未登记           → 走既有即时通道，行为与上一轮完全一致
```

### 1.3 既有通道的事实也进同一本台账

未登记时仍走即时通道，但 `mirror()` 会把**已验签**的事实写一条 `state='mirrored'` 记录：

- `pending()` 只取 `pending`，所以 mirrored 不会被规则拿走 → 不会重复建单；
- 验签失败（`bad-signature` / `bad-json` / 密钥缺失）**不留痕** —— 那本来就不是我们的事实；
- 价值：出问题时只看 `event-inbox-status` 一张表就能回答「这个仓库到底投过什么、我们收到了几条」，不用翻两套日志。

`status()` 相应新增 `claimed`（哪些来源由收件箱接管）与 `mirrored`（留痕条数），并附一句口径说明：**pending 与 mirrored 都不是失败**。

## 2. 验收矩阵扩到全视图

抽样会漏掉没被抽到的那个 —— 上一轮只测「概览 / 组织 / 验收」，而新加的「服务」「协作」「知识」「我的配置」全靠手工看过一眼。

现在覆盖 **7 视图 × 2 主题 × 1280/320 = 28 单元**，每个单元判四条硬线：

1. 页面级没有横向溢出；
2. 可聚焦元素都有可读名字、没有 `tabindex > 0` 劫持；
3. 逐键 Tab 落点按 DOM 顺序前进，6 次至少经过 3 个不同元素；
4. **不是白屏**：渲染节点数 < 12 直接报「疑似白屏」。

第 4 条是这轮加的，因为「能点开」经常被误当成「能用」—— 数据没到、模板没渲染的视图，前三条都会通过。

实测 28/28 全过，耗时从 44 秒（12 单元）增到约 78 秒，仍在可接受范围。

## 3. `parallel` 缺省按调度密度

### 3.1 为什么两头的缺省都不对

- **照搬上游「缺省 1」**（同组串行）：昨天的晨报还没验收完，今天 09:30 这班就被静默跳过 —— 人以为发了，其实没发。
- **上一轮的「缺省不限」**：分钟级巡检一旦上游卡住，同组会堆十几个同质任务，每个都在等人看。

### 3.2 现在的规则

```text
显式写 parallel        → 用它（source=explicit）
interval ≤ 60 分钟     → 缺省 1，串行（source=density）
其余（daily / cron / 事件）→ 缺省不限（source=unlimited）
```

理由写在 `routineParallel()` 的注释里：**高频例程堆积是资源问题，低频例程堆积是业务进度问题**。前者该挡，后者不该挡。

### 3.3 跳过不再静默

配额挡下时：

- 写 `events` 表 `routine-blocked:{id}`（`state='blocked'`），跨重启仍在；
- 审计 `routine.blocked`，同例行每小时最多一条（不刷屏）；
- `status()` 的每条例行带 `parallelSource` / `parallelReason` / `blocked`；
- 真的跑起来后把记录标成 `recovered`，不留过期误导。

`parallelReason` 直接给中文理由，例如「每 30 分钟一班属于高频例程，缺省串行以免堆积；要并行请显式写 parallel」。

## 4. 飞书这条：从「没有工单」到「通道体检说清楚」

「本轮没有新的飞书真实工单」这句话什么都说明不了：是通道坏了、凭据缺了、还是没人发？

新增只读动作 `channel-health`（`src/channel-health.ts`，纯函数、**不发任何外部请求**），每次看五条：

| 通道 | 判据 | 真实结果（2026-11-09 11:30） |
|---|---|---|
| 飞书 | 长连接状态 + 白名单 | **ready**（长连接已就绪 / 1 人 1 群） |
| GitHub | 轮询令牌 + webhook 密钥 | partial（两者都没配；gh CLI 已登录时轮询仍可用） |
| 通用事件源 | 登记了几个来源 | off（没登记，按需开启） |
| 钉钉 / 企微 | 出站 webhook | off（按需） |
| 真实工单证据 | 台账里 `oc_` / `ou_` 来源的任务 | **ready**（5 条，最近 SUI-135 / 11-08 11:22） |

三条口径写进了代码，不是文案：

1. **partial 不是失败**：能连但没人能发、能收但没有历史工单，都是 partial，不粉饰成 ready；
2. **不确定不判成坏**：GitHub 两把钥匙都没配时判 partial 而不是 blocked —— 轮询优先走 gh CLI，体检不探测登录态；
3. **connecting ≠ 断开**：刚启动几秒的长连接是 partial（「刚启动时正常」），只有 `disconnected` 才 blocked。

这轮实测还纠了自己一个错：第一版用 `feishuState === 'ready'` 当 `botReady`，重启后 8 秒内会显示「机器人身份未通过」—— 明显会吓人，才拆成四态。

控制台「服务」页新增「通道体检」卡：通道 / 方向 / 状态 / 依据 / 缺什么与下一步。

## 6. 如实边界（这一轮还剩什么）

1. **`mirror` 的台账会持续增长**：没有清理策略，长期跑要加保留窗口（与 `events` 表其他前缀一起治理）。
2. **通道体检不探测网络**：飞书判「长连接 ready」只证明监听进程在，不证明飞书服务端此刻可达；真正的可达性仍要看真实工单。
3. **GitHub 的 `gh` 登录态没被体检覆盖**：判 partial 是诚实的回避，不是解决。
4. **矩阵仍是「结构」检查**：28 单元能证明不溢出、不白屏、键盘可达，证明不了信息是否说得对 —— 那要靠人看截图。
5. **真实工单仍需人发**：体检能证明通道就绪、历史有 5 条，但「这一轮又发了一条」只能由人在飞书里做。
