# 派单多通道：三个可选方案（等用户选，未实现）

> 背景：主题已经能绑多个群，但**派单仍是单通道判定**——一条消息能落进哪个任务，
> 要同时过三道闸：准入三档（人是否被承认）+ IM 绑定（senderId / chatId 是否匹配）+ 归属校验（是不是这个任务的发起人）。
>
> 多通道一旦放开，风险不是「认不对」，而是**绕过这三道闸**。所以下面每个方案都要回答同一个问题：
> 换个群说话，凭什么还能进这个任务？

## 方案 A：显式指代优先（改动最小，推荐先做）

**规则**：消息里点名任务编号（`SUI-123` / `#123`）才允许跨频道接续；没点名的一律「旁听」。

- 旁听 = 写进该主题的讨论（advisory），不触发续跑、不唤醒执行端、不进验收。
- 点名后仍要过完整三道闸：准入 → 该任务是否属于这个主题 → 归属。
- 归属不符就拒绝并说明原因（复用现有 hand-back 口径）。

**代价**：说话的人要多打一个编号。
**好处**：可解释、可审计；错认的概率最低。
**失败模式**：编号打错 → 落到别人的任务 → 被归属校验挡住，报「Unauthorized: task IM binding」。不会静默错派。
**工作量**：小。`pass-through` 加一条「文本含任务编号」的显式指令识别 + 主题成员校验。

## 方案 B：主题级认领队列（目标形态，但要配界面）

**规则**：消息落到主题任一频道 → 先进「主题待认领」，由主题负责人（或规则）指派给某个任务；没指派就不执行。

- 认领需要一个入口：控制台「待认领」列表 + 群里一条认领提示。
- 超时未认领要提醒（否则消息静默堆积，比错派更糟）。

**代价**：多一个界面、多一个人工动作。
**好处**：最接近「群里说一句就有人接」，且责任落在主题负责人身上。
**失败模式**：无人认领 → 堆积。必须配超时提醒，否则等于把问题藏起来。
**工作量**：中。要认领数据模型 + 控制台视图 + 提醒。

## 方案 C：绑定频道 + 主题内转述（最保守）

**规则**：保持现有单通道绑定；主题内其它频道的消息只作为「转述建议」，由绑定频道负责人确认后才转发进任务。

**代价**：多一次人工确认，慢。
**好处**：几乎零风险，责任链最清楚。
**失败模式**：确认动作被忽略 → 消息停在「建议」状态。要能看到待确认数，否则又会变成堆积。
**工作量**：小到中。主要是转述状态的展示。

## 方案 D：加权仲裁（不建议）

按频道负责人权重 / 最近活跃度自动挑一个任务接续。**不建议**：选错了没人能解释为什么，而派单错一次的代价远大于慢一次。

## 我的建议

**先做 A，把 B 作为下一轮目标。**
理由：A 不需要新界面就能立刻解决「多个群都能说话」的场景，而且它天然守住三道闸；
B 更接近理想形态，但它真正的成本不在路由逻辑，而在「认领」这个人工环节和它的提醒。

C 可以随时作为兜底加进去，和 A 不冲突。

## 无论选哪个都必须守住的四条

1. **准入先行**：换了频道不等于换了身份，准入三档必须先过，`inferred` 档一律不建单。
2. **归属不放宽**：任务归属校验仍是最后一道，跨频道不能让「不是发起人的人」推进别人的任务。
3. **旁听要留痕**：没被采纳的消息也写进讨论，别让人以为「说了没人看」。
4. **不做静默兜底**：路由不了就说路由不了，不要「猜一个最像的」。
