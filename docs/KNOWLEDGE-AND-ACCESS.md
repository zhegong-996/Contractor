# 知识、授权与跨职能协作

2026-11-04。根据用户补充调整第一版：专业知识可以互动，原始上下文按对象授权。以下区分已经运行的代码、核读的上游能力和后续实现。

## 产品结构

公司共识、跨职能项目、专业空间是三个浏览维度。产研、增长、销售、职能是知识分类与责任分工，不是四座完全隔离的系统，也不是四个必须常驻运行的 Agent。一个项目可以跨专业；每个人和 Agent 只得到被授权的对象。

| 对象 | 结构化部分 | 非结构化部分 | 典型负责人 |
|---|---|---|---|
| 需求与产品判断 | 用户问题、目标、优先级、验收项、适用版本 | 访谈、需求说明、交互稿 | 产品负责人 |
| 研发知识 | 接口合同、提交 SHA、环境、测试结果、约束 | 设计决策、代码说明、故障复盘 | 技术负责人 |
| 增长实验 | 假设、渠道、样本、时间窗、指标口径、结果 | 素材、用户反馈、分析过程 | 增长负责人 |
| 销售经验 | 客户阶段、异议类别、方案版本、结果 | 沟通记录、演示材料、案例 | 客户负责人 |
| 职能知识 | 制度版本、生效期、适用人群、流程状态 | 制度原文、合同与办事说明 | 对应职能负责人 |

公司可共享经过确认的共识；项目参与者可共享项目合同；专业空间保留原始证据。标签本身不授予读取权限。员工任职、任务参与、材料所有者、授权对象和到期状态共同决定可见范围。

## 一个跨专业任务怎样发生

例如“提高门店试用后的付费转化”，销售提交反馈，产品与增长共用一个项目目标。

1. 销售负责人保留原客户沟通记录，提炼经过确认、适合项目参与者阅读的异议结论，附来源和适用范围。项目侧先读取这份结论。
2. 产品负责人形成需求与验收项。增长负责人关联实验口径；研发接到接口、实现边界、目标版本和必要证据。
3. Agent 发现证据不足，在原任务中提出具体材料申请。负责人可以共享某条任务、某份摘要，或开放所需专业项目。审批记录说明对象、接收人/Agent、用途与期限；目录可见不等于文档可读。
4. 所有工作沿用同一项目与关联任务。代码走 GitHub；增长实验和销售反馈保留自己的交付物。研发交付通过不自动等于增长目标达成。
5. 验收后，领域负责人确认可复用结论。结论有来源、版本、适用场景与失效条件；跨领域分歧保留为待确认事项。Agent 草稿不会自动成为公司制度。

跨部门授权的是材料和行动，不是把对方 Agent 的整段聊天、私人记忆、工具凭据全部复制过去。共享摘要也需要自己的可见范围；原始材料撤权后重新判断摘要是否还能独立保留。

| [Onyx](https://github.com/onyx-dot-app/onyx/blob/main/README.md) | 多源知识接入、检索、来源与权限元数据、MCP；CE/EE 分层 | 后续资料规模增大时评估为检索后端。来源 ACL 同步与所需连接器必须逐项核实版本/授权，不因仓库可见就认定 EE 能力可直接使用 |
| [OpenFGA](https://openfga.dev/docs/modeling/agents/task-based-authorization) | 用户、Agent、任务、工具资源的关系授权，任务/会话授权、条件到期、Agent 与任务绑定 | 作为以后跨多个业务系统的统一授权候选。第一版使用 Paperclip 现成 ACL，暂不再部署第二个权限引擎 |

这比从零写知识库、编辑器、检索、权限、调度更符合当前目标：只补系统之间的对象映射、版本证据和上下文选择合同。

## 当前代码实际实现

- 任务知识是 Paperclip 原生任务文档：专业标签、事实字段、正文、来源、适用范围、候选/确认/撤回和有效期。确认绑定具体修订；后续修改会使旧确认失效。
- Agent 可通过 MCP 提交自己的候选知识。确认和引用由本机操作者入口处理，Agent 工具中没有确认知识或验收的能力。
- 其他任务显式选择引用条目，每轮执行重读当前有效版本。源文档读取使用该 Agent 的原生 Paperclip 身份；本机管理身份不会代它绕过私有源 ACL。被撤回、过期、改成候选或失去源权限的内容停止加入新上下文。
- 所选源材料失效时，领取执行会停止，要求核对旧检查点；不能把保存下来的旧会话当作继续读取的授权。
- Wiki 共享入口只展示适合公司共享的资料与索引。受限材料继续放在受原生任务/项目 ACL 约束的文档；不自动复制进共享 Wiki，不自动跨团队检索。
- 第一轮只接飞书白名单单聊与获准测试仓库，使用真实消息 ID 去重和原消息回复。多用户、多部门和真实敏感材料仍待部署认证、来源权限映射及完整验收。

```text
飞书事件 → Paperclip 项目/任务/负责人 → 原生 ACL
                       ↓
任务需求 + 获准知识引用 + 检查点 → 当前执行上下文 → CLI / MCP
                       ↓
GitHub 提交 / 非代码交付物 → 指定版本验收 → 专业结论候选
                       ↓ 负责人确认、决定共享范围
专业知识 / 项目知识 / 公司共识 → 下一次任务显式引用
```

## 页面怎么使用已有部分

| 页面 | 第一期使用的已有部分 | 后续增量 |
|---|---|---|
| 工作台、项目、任务详情 | Paperclip 页面、成员、分配、运行、文档、交互 | 专业筛选；非代码任务交付类型 |
| 知识入口 | 原版 Wiki 页面、来源和修订；任务文档中的结构化结论 | 将“待确认、引用位置、访问范围”接到现有页面，不另做编辑器 |
| 专业空间 | 原生私有项目及任务分享面板 | 人员组与飞书组织映射，原知识库权限同步 |
| 申请访问 | 任务内原生提问/负责人处理；原生分享和撤销 | 按材料/用途/期限的申请表、到期撤权与输出受众校验 |
| 交接与验收 | 同一任务、同一工作树、任务文档、PR/CI/预览 SHA | 共享状态改变后的会话隔离、派生摘要和输出审查 |

已经获得的模型上下文无法通过一次撤权从模型内“收回”。当前阻止后续自动加载与继续领取；在多人生产环境上线前，还需要验证活动运行停止、派生内容、会话缓存、通知受众与外部模型发送边界。当前本机可信运行不能作为多人权限环境使用。

## 与玉伯思路的对应与证据限度

[原节目页面](https://www.xiaoyuzhoufm.com/episode/6ac8b67ce742e36efcc05e77) 的章节明确列出 01:31:46 用户上下文与人机交互、01:36:24 Context 的定义/存储/调用、01:41:03 UI，以及 00:45:01 组织方式。以上章节页已核读；页面不是逐字稿，官方评论提供的公众号文字版本次打开失败。因此“上下文作为有来源、有范围、持续更新的协作对象；授权在交互中完成”是本项目的应用设计，不冒充玉伯对权限框架的原话。

## 后续上线退出条件

先用测试资料完成：两个不同用户/专业 Agent 的正反向读写、按任务共享、换执行者重新检查、撤销后的搜索/引用/通知、来源过期、原系统撤权同步。通过后再接真实团队专业库。先实现可证明的单一授权链，不同时上线多个知识引擎。
