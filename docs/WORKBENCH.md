# 独立 SuitMe 协作台

从「项目」进入长期协作，按子项目或主题查找工单；在「协作」处理需要自己的答复与验收。发起人选择本次资料和协作对象。Super-agent 负责立项、授权范围和工单接续。AutoLoop 负责执行、等待、重试、复查与 CLI 会话。

| 产品行为 | 当前实现 |
| --- | --- |
| 项目与主题 | 项目按 `parent` 建立子项目，成员权限逐项目配置。项目维护人可建立主题和一层子主题；可独立交付的工作有各自的工单。大工单可拆子任务，也可关联已有工单。跨项目关联需获得两边的访问和发起权限。 |
| 项目资料 | 一个项目可引用飞书群、飞书文档、Figma 节点和多个 GitHub 仓库。来源保留各自的原地址、版本和用途。每个接收消息的来源有一个默认路由项目，可配置来源的默认主题。同一资料可登记在多个项目。 |
| 跨渠道接单 | 成员分别确认飞书和 GitHub 账号。两边显式引用同一个已接入的 Issue／PR，可以原子地关联同一张 Super-agent 工单。未确认的引用由项目维护人判断。已绑定来源的新 GitHub 评论可在原工单显示链接，原文由仓库配置选择是否共享。 |
| 「组」和「织」 | 职能、成员和 Agent 从配置定义。项目成员可直接委托有明确所有者的个人 Agent，或选择交给职能的专项 Agent。Agent 所有者可在界面上岗、停用。通过工单发起下一项协作时保留上游关系。 |
| 同工单接续 | 复用原版 Engine、Store、Effects 和 AutoLoop 原版调度及 worker。每次执行记录 Skill、上下文、授权资料和执行端版本。原生问答能延续 Codex 会话。项目会记录真实报出的 Token 和费用。 |
| 交付验收 | 仓库交付成员关联 PR 或分支提交。PR 保留 CI、审查、状态和历史提交，记录作者、提交者、推送者、委托人和 Agent 运行。验收由发起人按当前成果修订或已选提交签署。 |
| 知识与撤权 | 项目资料可含正文、类型、适用条件和来源。受限资料由所有者按工单、修订、读取 Agent 及其所有者授予八小时。验收结论经采用后入库，检索复用现有 BM25。撤权阻断后续装配，收回成果和派生知识的产品端访问，保留验收与审计记录。 |

协作可以登记业务指标、单位、基线和目标。交付验收后，发起人可以在工单记录实际值和依据，并把判断、适用条件和例外保存为知识候选。项目成员从已采用的经验发起下一张工单时，工作台会带上来源工单、经验版本和观测口径，以上次实测值作为新基线。Agent 收到授权的经验正文、适用条件和原观察依据。比较值来自实际记录，适用范围随来源权限复核。

## 本机启动

运行 `git submodule update --init --recursive` 和 `npm ci`。为独立实例选定绝对路径并准备本地配置。

```sh
export COLLAB_STATE_DIR="$PWD/.runtime/workbench"
mkdir -p "$COLLAB_STATE_DIR"
cp -n fixtures/workbench.example.json "$COLLAB_STATE_DIR/workbench.json"
npm run workbench -- init-owner product
npm run workbench -- add-member design operator
npm run workbench -- add-member engineering operator
npm run workbench
```

账号初始化命令从标准输入读取口令，直接在终端执行时输入口令后按 Ctrl+D 结束输入。用受信任的本机登录配置运行执行端。打开 [本机工作台](http://127.0.0.1:4280/)，工作台仅监听回环地址。独立数据保存在配置目录，原宿主及上一轮测试工单有各自的账本。

飞书可选。配置 `feishu.profile`、`appId`、`botId`，项目资源登记真实 chat ID 并确认归属。原单渠道模式通过创建成员时填写机器人应用下的 open ID 建立身份关联。发送 `/协作 agent-id 需求`，群聊需点名机器人。已绑定成员在原话题可用 `/答 序号` 或 `/答 答复内容`。一个机器人接收入口只应由一个实例写入。

启用飞书时，`GET /health` 会报告 `feishu.state` 和订阅启动次数。订阅断开时返回 503 并按间隔自动重连，收到 CLI 就绪信号后恢复 200。工单接口在重连期间仍可使用。

## 跨渠道测试入口

在独立测试配置增加 `"crossChannel": { "githubPollSeconds": 30 }`。登记并绑定测试群与测试仓库，运行进程使用已授权读取该仓库的 `gh`。旧飞书接入配置和测试实例的账本分开保管。跨渠道模式使用工作台验证后的绑定。

- 登录协作台，在「渠道账号」生成各自的十分钟一次性验证命令。飞书在机器人单聊发送，GitHub 用本人账号在已接入的私有仓库中新发 Issue 评论。协作台收到命令后，核对来源账号并确认。仅受理绑定生效期间发出的新命令。
- 在已接入的飞书群 @ 机器人，或在 GitHub Issue 中用新评论发送 `/协作 auto [Issue或PR完整链接] 需求`。也可填写已登记的 Agent 标识和现有工单标识。来源、回复原消息和明确引用共同核对。接续原单时保留讨论，Agent 在下一次获准运行时可读取相同项目内仍有权限的补充。
- 新话题无明确引用、来源冲突或牵头职责未确定时，进入项目维护人的待办。维护人可将一条消息记到项目或主题、挂回旧单，或另建工单。确认时重查引用，若已归入同一工单则优先续单。明确需要另开时传入 `separate: true`。选择在相关项目建单时，两边均须授权，并由目标项目维护人填写可在目标项目分享的任务说明。
- 接入采用 Super-agent 原版 Feishu／GitHub 事件转换、Engine、Store 与 AutoLoop worker。GitHub 轮询以评论 ID 关联观察到的内容修订，已编辑评论仅作为证据，无法触发委托或账号验证。仓库开启 `shareNotes` 才共享非敏感评论正文，否则保存时间和内容指纹。Figma 关联目前为资料入口。

## 飞书群消息整理

仅处理项目内已绑定且显式开启 `digest: true` 的飞书群。项目的 `discussion.agent` 选一个现有在岗 Agent，`discussion.model` 可选用已接模型，Codex 整理默认用低推理强度。`discussion.cron` 默认 `0 0,12 * * *`，即上海时间每天 00:00 和 12:00，按十二小时窗口整理。已有 `/协作` 和 `/答` 仍按即时入口处理。群整理沿用 AutoLoop 原版规则和 worker，在无候选的时段直接结束。重启后从已保存的位置继续。

- 机器人收到普通群文字时实时收集。若机器人只能收到 `@`，可设置 `discussion.history` 的 `profile`、`appId`、`userOpenId` 与 `member`，让已授权的项目维护人账号在整理时间窗内补读同一群。系统先核对当前登录身份，按原消息 ID 去重；不会把其他飞书应用里的 open ID 猜成同一个人。各群从开启时开始读取。每批最多处理 30 条候选，每条给模型最多 600 字，积压由随后窗口继续，未整理原文最多保留三天。
- `discussion.documents` 只填写项目已绑定且允许用于整理的飞书 Docx 链接。带区块锚点的链接只读该区块，每次核对读取身份及修订号。还会检索当前项目已发布的公开项目资料、已有工单、已绑定 GitHub 仓库的明确引用和最近 30 天相近的工作标题。未确认或失效的依据不能作为自动归属证据。
- 闲聊和常见凭据先在本地过滤。整理结果可以记到项目或主题，也可按已确认的引用回到原工单讨论。原工单记录该反馈，现有验收不变，Agent 在下一次获准执行时可读取这条补充。独立的新工作形成开单建议，负责人选 Agent 后才立项；只有归属或范围不明确的事项进入负责人待办。普通反馈的摘要不直接写入团队知识。
- 群中不发整理广播。项目成员可查看已归档摘要与来源；待判断和开单建议仅项目维护人可处理。联调环境的机器人订阅未收到无 `@` 的测试消息，已授权账号的按窗补读链路已经实跑。

每条原消息都有自己的来源和已观察版本。同批、同回复范围的相同文字可共同归纳。原消息撤回时删除其正文和来源关联，仍有来源的归纳继续有效。按半天补读时轮转复查每群最多 50 条已知消息，新修订通过原 ID 归入同一条记录。重新读取无法恢复两次读取之间平台未返回的中间版本。历史摘要标明所依据的修订号，已有归档的后续编辑只增加版本证据。

维护人可通过 `GET /api/discussion/<项目>/revisions/<消息ID>` 查看当前仍可核对的飞书版本。 `POST /api/discussion/<整理记录ID>/resolve` 接受可选的 `message` 字段来决定单条来源，省略时继续处理整条待确认归纳。

Super-agent 复用了原版消息归一、话题根、来源准入策略和人工确认后的建单。分批、防重复与失败后的恢复参考 [LobeHub 的定时整理](https://github.com/lobehub/lobehub/blob/a8424d204a7ed1eb36985ebdfa6eac8041615392/apps/server/src/services/agentIdentity/wake/digest.ts)，按现有 AutoLoop 原版调度和 SuitMe 项目授权实现。

## 派工与人工决定

- 每个项目可设置 `decisionOwner` 为接单决策人，默认取可处理任务的首位维护人。`dispatch` 的每条规则填写 `function`、`agent` 和可选的 `topic`、`decider`。自动派工依次查当前主题、父主题和项目默认规则。符合条件的牵头 Agent 唯一且在岗时自动选择。职责重叠时由维护人选择。
- 在 `GET /api/needs-you` 查看本人的接单确认、群消息建议、执行追问、资料授权、阻塞和验收。已有绑定的飞书账号收取机器人私聊。私聊带待办编号，执行决策人可回复 `/答 待办编号 序号或答复`。涉及受限资料的问题只给工单发起人，通知省略资料正文。
- 同一执行范围内的 `ask` 都是必答事项。存在未答事项时，下一轮保留在 AutoLoop 队列，补充消息、已答事项和到期复查继续合并。全部答复后才领取执行；其他工单可以继续。交接也须先答完必答事项，Agent 不能代替人结清问题。原生上下文中的未结卡片按本工单执行范围过滤。`notice` 保留原生告知语义，不参与必答检查。SuitMe 的 `execution-gates.ts` 在原生 `commitLatest` 事务内用临时 View 过滤候选，再调用原版 `decide(claimNext)`，按完整队列重算原生期限；没有改写上游投影、取消等待轮或新建第二套调度器。
- `POST /api/ticket/<工单>/handoff` 接受维护人选择的在岗 `agent` 和交接 `reason`。工作台先取消排队、请 AutoLoop 停止旧进程。确认运行停止并记录证据后，调用 Super-agent 原生重派接口，同一工单和 Mandate 接续到新 Assignment。旧会话、卡片和定时回查留在旧执行范围。旧运行失联时等待回执并提醒维护人。
- 本机适配层在启动、心跳和取消时记录进程身份及观测到的后代，取消同时覆盖脱离原进程组的子进程。退出确认须等这些进程消失，信息无法核对时继续等待。记录只保留进程标识、启动时间和可执行名指纹，不保存命令参数或环境变量。
- 接替 Agent 的受限资料权限单独核对，缺少授权时旧执行保持停止、交接等待资料负责人。撤权或到期后重新申请产生新申请编号和新的负责人待办／飞书通知，同轮重复请求保持幂等。旧申请不能批准新一轮。升级前未记录读取 Agent 的历史授权保留审计，但需重新明确授权才能使用。
- 多份资料分别记录申请与批准，一份资料的申请不能代替其他资料。恢复中缺少任一份授权都继续等待；对已明确撤销的对应申请，仍需主动重申，后台不会反复自动请求。
- 每次执行记录资料所用的具体授权申请编号。撤权后即使迅速重新批准，旧回执仍按旧授权隔离。恢复复用原生停止回执与进程退出证据，保留原工单必答卡，以新资料快照和新的 CLI 会话继续；重新授权不恢复旧成果的可读性。
- 后端的研发接单、确认口径与代码交接、阻塞接续、打回修改及逐版验收见 [原工单多轮交付](WORKBENCH-ITERATIONS.md)。待验收成果的独立查阅重授权与继续执行分开记录；本轮尚未增加前端入口。

## 项目、资料与提交

- `projects[].parent` 指向上级项目，`relatedProjects` 登记有协作关系的项目。每个项目分别校验成员和资源权限。主题和子主题用于归纳多轮工作。父子工单用于拆分交付，关联工单用于连接各自独立负责和验收的工作。
- 在项目页关联飞书文档、Figma 文件或节点及其他 HTTPS 文档。Backstage 的 `parseEntityRef` / `stringifyEntityRef` 给项目来源提供稳定引用；经工作台选入工单的引用和版本进入执行记录。链接正文仍由源站授权。
- 仓库来源 `purpose` 为 `delivery`。`contributors` 指定可以挂交付证据的项目成员，`execution.base` 与 `execution.paths` 指定代码委托的基线和可交付路径。可用 `route: false` 在另一项目将同一仓库用作交付目标，已授权成员可用明确工单标识核对归属。
- `attribution.checkouts` 为交付仓库指定专用本地副本，`attribution.entireCommand` 指向 Entire CLI。代码任务先获取远端基线，宿主保管工单 worktree，Codex 在成员隔离的文件副本中执行。停止后才核对并移交受托差异、记录本地提交；研发通过自己有权的账号推送并关联 PR。Agent 不继承 GitHub 凭据。配置与边界见 [成员执行隔离](MEMBER-EXECUTION-ISOLATION.md)。
- GitHub 的 Issue 和 PR 用仓库 ID 与各自编号定位，分支用仓库和引用名定位，再记录实际提交哈希。已关联的普通评论和 PR 状态更新只增加来源记录或更新交付。按 `base SHA + head SHA` 保留交付版本，项目成员可以回看；关 Issue 或改 PR 状态不会签署业务验收。
- 代码工单关联与验收时核对当前成果对应的运行和受托提交。PR 的仓库、head 分支、head SHA、base 分支与基线必须匹配本单执行记录；验收重新读取该 SHA 最新的 GitHub Actions `collab-pilot` 检查，保存检查编号和版本。缺少 PR／提交、其他工单的 PR、旧版本 CI、草稿或已关闭且未合并的 PR 都不能验收。资料整理类成果仍按自身成果修订验收。
- 交付成员首次关联 PR 后，下一版由 GitHub 轮询跟踪同一 PR 上的受托提交与对应 CI。缺证据或 CI 失败先通知本版研发，通过后通知发起人验收。研发可以拒接、退回或确认委托，负责人可在原单重新安排。后端接口见 [交付通知与研发退回](WORKBENCH-ITERATIONS.md#交付通知与研发退回)。
- Entire 安装本地 hooks，由 `checkpoint explain --json --commit` 读取检查点元数据。工作台用已登记的精确仓库、提交和执行记录归因；只有对应的 Agent 会话也被 Entire 确认时，界面才显示「会话已核对」。GitHub 的账号和记录保留原始信息，可与已验证的内部成员映射一同查看。

## 当前范围

- 人员、职责、项目和执行端的初始配置通过本地文件管理。注册表保留 Codex、Cursor、Claude Code、ACP 和通用 CLI 类型；当前生产派工只启用完成隔离适配的 Codex + OpenAI。其他 CLI 暂时明确阻断，不继续共享宿主凭据运行。此前 Cursor 实跑是引入隔离前的历史证据。
- 已接原版观察准入、执行规则、重试、手动停止、问题卡片、会话和定时复查。独立入口还需接通其他来源和通知插件、自动派生与分布式接续、交付发布插件和组织级费用结算。
- PR 推送与创建由研发完成。CI 验收使用项目约定的 `collab-pilot` 检查。外部资料正文在配置允许的范围内读取，GitHub 评论保留已观察的编辑版本。
- 产品端按权限隐藏来源正文和派生成果。Codex 的工作区、登录、会话、上下文与临时目录已按执行授权范围隔离，不能读取宿主 worker 历史或其他成员目录。交接时不复制旧会话。宿主私有账本仍保留审计记录，不承诺删除外部已公开代码或对宿主管理员保密。
- 本机进程跟踪覆盖已观测的进程谱系，不能提供容器或操作系统作业级隔离。首次观测前已完全脱离的守护进程不能仅靠轮询证明归属；生产执行端仍需受控的进程容器。短命令采用原生退出文件与进程组消失作为退出证据。
- 现有内容索引与来源关系支持查证。验收后可从已确认问题及成果生成带出处的工作记录候选，所有者先核对内容与适用条件，再决定是否采用。新复核动作目前只接后端。通用模型知识提炼、知识替代／失效管理、组织知识图谱及经过验证的轻量模型服务仍待接入。
- 每次实际执行保存 Skill、上下文与运行配置快照，读取时重新核权。模型和成员凭据必须显式配置；分别记录请求的模型和 CLI 会话回报。计量保存逐次原始回执，取消也保留已发生消耗，缺失金额明确为未知。配置预算时，缺价会阻止下一次执行，当前不能在单轮生成途中按金额截停。完整差距及验证范围见 [文档九点核验](PRODUCTION-CAPABILITY-AUDIT.md)。

## 运行证据

2026-11-14，独立工作台通过三个分别登录的测试账号完成了门店预约提醒协作。产品账号委托设计成员的个人 Agent；设计账号授权受限资料；工程账号的正文查询、授权、答复与验收被拒；真实 Codex 经原版 AutoLoop 发出问题并用了同一会话接续。验收使用测试账号签署，系统核对已有 GitHub PR 的真实 head 和 CI，拒绝另一提交。知识采用后可检索，撤权后原工单成果及派生知识不可读，验收记录仍保留。已在浏览器检查委托入口、资料引用、撤权状态和 390 像素宽度下的页面。

这轮用独立测试账号走通额外的一次经验复用。设计 Agent 的预约入口意见先由产品验收，产品记录测试页浏览器复核依据并采用经验。工程账号由此创建关联工单，沿用观测指标和上次实测值。真实 Codex 读取授权经验，再完成一轮工程复查。两次观测属于联调样例，初始基线用于验证界面与数据链路。实测样例未覆盖真实门店转化。

同日，在独立跨渠道实例、私有飞书测试群和私有 GitHub 测试仓库用门店推荐理由样例联调。飞书本人单聊与 GitHub 本人评论完成账号验证。两边并行提交后归入一张工单，Codex 通过 AutoLoop 完成一个运行。无引用的后续消息进入待确认，维护人在浏览器将其挂回原工单。解除 GitHub 绑定后，新评论未进入工单或待确认区。

随后在门店推荐项目下用独立的产品、设计和研发测试登录验证分工。飞书测试群、飞书产品说明、Figma 节点和研发仓库登记在同一项目。推荐理由文案和「小屏展示」子主题里的换行问题各有工单，互相可见。已关联 GitHub Issue 的开关和 PR 的草稿变更回写到各自来源，工单和 Agent 运行数量保持。三条 PR 分别由人工、Codex、Cursor 产生改动，并由本次授权的 GitHub 账号推送。两个 Agent 提交的委托归因来自 SuitMe 执行记录；它们未产生可验证的 Entire 原生检查点。各测试登录由同一操作者扮演，外部平台上没有借此模拟真实不同的账号所有人。

群消息整理在同一试点里用真实飞书消息、已有测试仓库的 Issue 和飞书文档修订 3 验证。为缩短验证时间，临时使用短定时窗口。重复的小屏反馈折为一条，原工单没有新增运行；闲聊过滤，另外留下项目进展、主题观察、独立新单建议和需判断的事项。用测试产品登录把需判断事项放回主题，并把独立建议发起成一张工单；重复提交返回原工单。设计测试登录可查看已整理反馈，不能代项目维护人确认；非项目登录无法读取该项目整理。联调结束后恢复半天节奏。

2026-11-15，在独立后端实例完成「门店推荐理由」必答、授权和代码验收联调。真实飞书测试群发起后，双必答执行端产生两条真实私聊待办，答一条仍等待，全部答复后只接续一次；该双问题执行端为受控 CLI，用于验证调度，不代表模型判断质量。代码工单则由真实 Codex 澄清，撤权后重新申请产生新的资料负责人通知，旧批准被拒。更换到不同测试成员所有的 Codex 后，单独申请资料权限，旧执行停止且新授权生效后才开始实现。

首次代码交接发现 Codex 的工具子进程脱离原进程组后仍存活。该次失败保留，人工清理不计为通过。增加进程谱系核验后重新实跑：旧 Codex 及其受控子进程自动退出，接替执行再启动。成功工单仅有澄清、被取消的接续、接替实现三个运行，以及原委托和交接两次 Assignment。两份资料同时撤权的额外实跑也验证了独立申请、两条真实飞书通知、部分批准仍等待、必答保留及同单单次接续。

真实交付为 [测试仓 PR #10](https://github.com/zhegong-996/desktop-tutorial/pull/10)，提交 `aff234483de4079207e0cad273c97ea522af2f9f`，对应 [CI 运行](https://github.com/zhegong-996/desktop-tutorial/actions/runs/43678995071) 成功。未关联 PR、缺少提交、错误提交、其他成员代验收均被拒；发起人测试账号随后按该提交签署验收，知识保存为候选，未自动采用。GitHub 本人评论与飞书补充回到原单，没有新增派工。连接器代发评论带 GitHub App 标记，按既有入口策略过滤，本轮未放宽应用代发的信任范围。
