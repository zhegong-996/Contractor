# 独立 SuitMe 协作台

从「项目」进入长期协作，按子项目或主题查找工单；在「协作」处理需要自己的答复与验收。发起人选择本次资料和协作对象。Super-agent 负责立项、授权范围和工单接续。AutoLoop 负责执行、等待、重试、复查与 CLI 会话。

| 产品行为 | 当前实现 |
| --- | --- |
| 项目与主题 | 项目按 `parent` 建立子项目，成员权限逐项目配置。项目维护人可建立主题和一层子主题；可独立交付的工作有各自的工单。大工单可拆子任务，也可关联已有工单。跨项目关联需获得两边的访问和发起权限。 |
| 项目资料 | 一个项目可引用飞书群、飞书文档、Figma 节点和多个 GitHub 仓库。来源保留各自的原地址、版本和用途。每个接收消息的来源有一个默认路由项目，可配置来源的默认主题。同一资料可登记在多个项目。 |
| 跨渠道接单 | 成员分别确认飞书和 GitHub 账号。两边显式引用同一个已接入的 Issue／PR，可以原子地关联同一张 Super-agent 工单。未确认的引用由项目维护人判断。已绑定来源的新 GitHub 评论可在原工单显示链接，原文由仓库配置选择是否共享。 |
| 「组」和「织」 | 职能、成员和 Agent 从配置定义。项目成员可直接委托有明确所有者的个人 Agent，或选择交给职能的专项 Agent。Agent 所有者可在界面上岗、停用。通过工单发起下一项协作时保留上游关系。 |
| 同工单接续 | 复用原版 Engine、Store、Effects 和 AutoLoop 原版调度及 worker。每次执行记录 Skill、上下文、授权资料和执行端版本。原生问答能延续 Codex 会话。项目会记录真实报出的 Token 和费用。 |
| 交付验收 | 仓库交付成员关联 PR 或分支提交。PR 保留 CI、审查、状态和历史提交，记录作者、提交者、推送者、委托人和 Agent 运行。验收由发起人按当前成果修订或已选提交签署。 |
| 知识与撤权 | 项目资料可含正文、类型、适用条件和来源。受限资料由所有者按工单和修订授予八小时。验收结论经采用后入库，检索复用现有 BM25。撤权阻断后续装配，收回成果和派生知识的产品端访问，保留验收与审计记录。 |

协作可以登记业务指标、单位、基线和目标。交付验收后，发起人可以在工单记录实际值和依据，并把判断、适用条件和例外保存为知识候选。项目成员从已采用的经验发起下一张工单时，工作台会带上来源工单、经验版本和观测口径，以上次实测值作为新基线。Agent 收到授权的经验正文、适用条件和原观察依据。比较值来自实际记录，适用范围随来源权限复核。

## 本机启动

运行 `git submodule update --init --recursive` 和 `npm ci`。为独立实例选定绝对路径并准备本地配置。

```sh
export COLLAB_STATE_DIR="$PWD/.runtime/workbench"
mkdir -p "$COLLAB_STATE_DIR"
cp -n fixtures/workbench.example.json "$COLLAB_STATE_DIR/workbench.json"
npm run workbench -- init-owner product
npm run workbench -- add-member design operator
npm run workbench -- add-member engineering operator
npm run workbench
```

账号初始化命令从标准输入读取口令，直接在终端执行时输入口令后按 Ctrl+D 结束输入。用受信任的本机登录配置运行执行端。打开 [本机工作台](http://127.0.0.1:4280/)，工作台仅监听回环地址。独立数据保存在配置目录，原宿主及上一轮测试工单有各自的账本。

飞书可选。配置 `feishu.profile`、`appId`、`botId`，项目资源登记真实 chat ID 并确认归属。原单渠道模式通过创建成员时填写机器人应用下的 open ID 建立身份关联。发送 `/协作 agent-id 需求`，群聊需点名机器人。已绑定成员在原话题可用 `/答 序号` 或 `/答 答复内容`。一个机器人接收入口只应由一个实例写入。

## 跨渠道测试入口

在独立测试配置增加 `"crossChannel": { "githubPollSeconds": 30 }`。登记并绑定测试群与测试仓库，运行进程使用已授权读取该仓库的 `gh`。旧飞书接入配置和测试实例的账本分开保管。跨渠道模式使用工作台验证后的绑定。

- 登录协作台，在「渠道账号」生成各自的十分钟一次性验证命令。飞书在机器人单聊发送，GitHub 用本人账号在已接入的私有仓库中新发 Issue 评论。协作台收到命令后，核对来源账号并确认。仅受理绑定生效期间发出的新命令。
- 在已接入的飞书群 @ 机器人，或在 GitHub Issue 中用新评论发送 `/协作 agent-id [Issue或PR完整链接] 需求`。也可用现有工单标识。链接须能在本项目核对。已关联话题可续接，工单保留两个入口与发言来源。
- 新话题没有明确引用时，「待确认工单归属」由维护人选择关联已有工单、确认新建或忽略。关联消息进入讨论记录，已有工单的 Agent 派单次数不变。
- 接入采用 Super-agent 原版 Feishu／GitHub 事件转换、Engine、Store 与 AutoLoop worker。GitHub 命令由本机轮询读取，飞书使用已有事件通道。普通飞书群消息、历史评论编辑和跨渠道对话转发在此模式下不处理。Figma 关联目前为资料入口。

## 项目、资料与提交

- `projects[].parent` 指向上级项目。项目可以直接有工单，也可以建立主题和子主题来整理多轮工作。点击上级主题可以看到两个层级的工作。父子工单用于同一交付的拆分；「关联已有工单」可连接各自独立负责和验收的工作。
- 在项目页关联飞书文档、Figma 文件或节点及其他 HTTPS 文档。Backstage 的 `parseEntityRef` / `stringifyEntityRef` 给项目来源提供稳定引用；经工作台选入工单的引用和版本进入执行记录。链接正文仍由源站授权。
- 仓库来源 `purpose` 为 `delivery`。`contributors` 指定可以挂交付证据的项目成员；`execution.base` 与 `execution.paths` 指定代码委托的基线和可交付路径。可用 `route: false` 在另一项目将同一仓库用作交付目标，带明确工单标识的请求仍可定位。
- `attribution.checkouts` 为交付仓库指定专用本地副本，`attribution.entireCommand` 指向 Entire CLI。选择开发仓库的 Codex 或 Cursor 任务先获取远端基线，在工单专用 worktree 中执行。工作台检查改动范围、记录本地提交，研发通过自己有权的账号推送并关联 PR。因权限、基线或交付范围变化而被阻断的任务会显式提示。
- GitHub 的 Issue 和 PR 用仓库 ID 与各自编号定位，分支用仓库和引用名定位，再记录实际提交哈希。已关联的普通评论和 PR 状态更新只增加来源记录或更新交付。按 `base SHA + head SHA` 保留交付版本，项目成员可以回看；关 Issue 或改 PR 状态不会签署业务验收。
- Entire 安装本地 hooks，由 `checkpoint explain --json --commit` 读取检查点元数据。工作台用已登记的精确仓库、提交和执行记录归因；只有对应的 Agent 会话也被 Entire 确认时，界面才显示「会话已核对」。GitHub 的账号和记录保留原始信息，可与已验证的内部成员映射一同查看。

## 当前范围

- 人员、职责、项目和执行端的初始配置通过本地文件管理。Agent 运行端支持按配置选择 Codex、Cursor、Claude Code、ACP 和通用 CLI，本轮实跑覆盖 Codex 和 Cursor。
- 已接原版观察准入、执行规则、重试、手动停止、问题卡片、会话和定时复查。独立入口还需接通其他来源和通知插件、自动派生与分布式接续、交付发布插件和组织级费用结算。
- PR 推送与创建由研发完成。CI 验收仍使用项目约定的 `collab-pilot` 检查。这轮实际运行使用已有私有测试仓库的独立分支，三条 PR 未合并，未部署或确认业务验收。自动拉取外部正文、普通飞书群消息整理和 GitHub 评论编辑版本尚未接入。
- 产品端按权限隐藏来源正文和派生成果。执行端已收到的数据仍可能保存在本机 worker 与 CLI 会话文件，生产部署需要按执行身份隔离这些目录和凭据。独立工作台这轮使用虚构业务资料。
- 现有内容索引与来源关系支持查证。组织知识图谱、自动知识候选提炼，以及经过验证的轻量模型服务仍待接入。当前只读取执行端配置中的模型，执行端缺少报价时，界面显示未回传。

## 运行证据

2026-11-14，独立工作台通过三个分别登录的测试账号完成了门店预约提醒协作。产品账号委托设计成员的个人 Agent；设计账号授权受限资料；工程账号的正文查询、授权、答复与验收被拒；真实 Codex 经原版 AutoLoop 发出问题并用了同一会话接续。验收使用测试账号签署，系统核对已有 GitHub PR 的真实 head 和 CI，拒绝另一提交。知识采用后可检索，撤权后原工单成果及派生知识不可读，验收记录仍保留。已在浏览器检查委托入口、资料引用、撤权状态和 390 像素宽度下的页面。

这轮用独立测试账号走通额外的一次经验复用。设计 Agent 的预约入口意见先由产品验收，产品记录测试页浏览器复核依据并采用经验。工程账号由此创建关联工单，沿用观测指标和上次实测值。真实 Codex 读取授权经验，再完成一轮工程复查。两次观测属于联调样例，初始基线用于验证界面与数据链路。实测样例未覆盖真实门店转化。

同日，在独立跨渠道实例、私有飞书测试群和私有 GitHub 测试仓库用门店推荐理由样例联调。飞书本人单聊与 GitHub 本人评论完成账号验证。两边并行提交后归入一张工单，Codex 通过 AutoLoop 完成一个运行。无引用的后续消息进入待确认，维护人在浏览器将其挂回原工单。解除 GitHub 绑定后，新评论未进入工单或待确认区。

随后在门店推荐项目下用独立的产品、设计和研发测试登录验证分工。飞书测试群、飞书产品说明、Figma 节点和研发仓库登记在同一项目。推荐理由文案和「小屏展示」子主题里的换行问题各有工单，互相可见。已关联 GitHub Issue 的开关和 PR 的草稿变更回写到各自来源，工单和 Agent 运行数量保持。三条 PR 分别由人工、Codex、Cursor 产生改动，并由本次授权的 GitHub 账号推送。两个 Agent 提交的委托归因来自 SuitMe 执行记录；它们未产生可验证的 Entire 原生检查点。各测试登录由同一操作者扮演，外部平台上没有借此模拟真实不同的账号所有人。
