# 独立 Contractor

企业可在平台管理中选择主 IM 登录渠道。成员开通、原账号迁移及回调设置见 [企业主 IM 登录](WORKBENCH-IM-LOGIN.md)。

从「项目」查看长期协作，按子项目或主题查找工单。在「待我处理」找到需要自己答复、授权与验收的事项。发起人选择本次资料和协作对象。Super-agent 负责立项、授权范围和工单接续。AutoLoop 负责执行、等待、重试、复查与 CLI 会话。

| 产品行为 | 当前实现 |
| --- | --- |
| 项目与主题 | 项目按 `parent` 建立子项目，成员权限逐项目配置。项目维护人可建立主题和一层子主题；可独立交付的工作有各自的工单。大工单可拆子任务，也可关联已有工单。跨项目关联需获得两边的访问和发起权限。 |
| 项目资料 | 一个项目可引用飞书群、飞书文档、Figma 节点和多个 GitHub 仓库。来源保留各自的原地址、版本和用途。每个接收消息的来源有一个默认路由项目，可配置来源的默认主题。同一资料可登记在多个项目。 |
| 跨渠道接单 | 成员分别确认飞书和 GitHub 账号。两边显式引用同一个已接入的 Issue／PR，可以原子地关联同一张 Super-agent 工单。未确认的引用由项目维护人判断。已绑定来源的新 GitHub 评论可在原工单显示链接，原文由仓库配置选择是否共享。 |
| 「组」和「织」 | 职能、成员和 Agent 从配置定义。项目成员可直接委托有明确所有者的个人 Agent，或选择交给职能的专项 Agent。Agent 所有者可在界面上岗、停用。通过工单发起下一项协作时保留上游关系。 |
| 同工单接续 | 复用原版 Engine、Store、Effects 和 AutoLoop 原版调度及 worker。每次执行记录 Skill、上下文、授权资料和执行端版本。原生问答能延续 Codex 会话。项目会记录真实报出的 Token 和费用。 |
| 交付验收 | 仓库交付成员关联 PR 或分支提交。PR 保留 CI、审查、状态和历史提交，记录作者、提交者、推送者、委托人和 Agent 运行。验收由发起人按当前成果修订或已选提交签署。 |
| 知识与撤权 | 项目资料可含正文、类型、适用条件和来源。受限知识的负责人可选择隐藏目录，或仅展示标题并允许申请。正文由负责人按工单、修订、读取 Agent 及其所有者授权，有效期由项目维护人设定，默认八小时。验收结论经采用后入库。撤权阻断后续装配，收回成果和派生知识的产品端访问，保留验收与审计记录。 |

协作可以登记业务指标、单位、基线和目标。交付验收后，发起人可以在工单记录实际值和依据，并把判断、适用条件和例外保存为知识候选。项目成员从已采用的经验发起下一张工单时，工作台会带上来源工单、经验版本和观测口径，以上次实测值作为新基线。Agent 收到授权的经验正文、适用条件和原观察依据。比较值来自实际记录，适用范围随来源权限复核。

## 页面入口

- 「待我处理」集中显示当前登录成员须答复、授权、确定归属、接单或验收的事项。点入相应工单或项目后直接处理。
- 「协作工单」左栏按状态和主题定位，右侧在同一工单切换协作动态、交付与验收、上下文。交接、接续和历史执行均以当前工单为索引。
- 「知识库」按现行、待确认和历史版本检索。采用时显示来源与适用条件，可携带现行知识发起下一项协作。
- 「Agent」按当前项目查看职责、所有者、委托记录及模型费用回执。项目页集中显示子项目、主题、来源连接、群反馈和成员分工。
- 「协作动态」显示当前版阻塞、处理人和下一步，按现有权限跳到执行快照、授权或交付。执行端区分离线、暂停、丢失和退役。退役登记只能重新配对，丢失设备须由设备所有者确认找回并重新核对项目授权。
- 「平台管理 → 模型服务」由有服务管理权限的平台成员配置现有 OpenAI、DeepSeek、Ollama 适配的启用状态及允许模型。设置在新执行领取时生效。模型凭据和执行端注册来自原有可信配置。
- 「项目 → 职责与路由」由项目维护人分配现有职责、选主题牵头 Agent 和决定人，并按用途配置已获准的本机 Codex 主备模型。项目和平台设置存入工作台账本，保存时检查所编辑的修订。已有派工、历史工单及执行证据按原记录查阅。
- 「资料与连接」显示当前项目的 GitHub 和 IM 状态。可配置补读的飞书来源向维护人显示最近核对结果。Figma 资料负责人可核对源站状态与修订，进入对应知识候选。「平台管理 → 服务状态」显示飞书收件与回调、知识索引和待补写回执的汇总。公开 `/health` 仅列 GitHub 连接状态，仓库明细从项目读取。

侧栏、基础控件与状态视图使用 Ant Design 和 Contractor 组件。列表与详情联动、Agent 档案及工单证据使用同一套 Contractor 登录和后端接口。[组件来源](SOURCES.md)

## 本机启动

运行 `git submodule update --init --recursive` 和 `npm ci`。为独立实例选定绝对路径并准备本地配置。

```sh
export COLLAB_STATE_DIR="$PWD/.runtime/workbench"
mkdir -p "$COLLAB_STATE_DIR"
cp -n fixtures/workbench.example.json "$COLLAB_STATE_DIR/workbench.json"
npm run workbench -- init-owner product
npm run workbench
```

样例配置不包含业务项目、职责或 Agent。使用所有者账号登录后先创建项目，再按需要配置项目成员、职责、Agent、模型和 Worker。需要额外测试账号时，可运行 `npm run workbench -- add-member <username> <role>` 创建。

账号初始化命令用于本机引导和测试，从标准输入读取口令，交互终端隐藏输入，回车确认。团队在网页登录页选择「开通账号」，用企内飞书单聊应用机器人发送验证命令。平台管理员在「平台管理 → 账号开通申请」核对飞书姓名并批准角色，申请人回到发起页自行设置口令，飞书身份随首次开通绑定。账号开通后，由项目维护人另行授予项目权限。

启动命令先构建本地前端，再启动 HTTP 服务。用受信任的本机登录配置运行执行端。打开 [本机工作台](http://127.0.0.1:4280/)，工作台仅监听回环地址。独立数据保存在配置目录，原宿主及上一轮测试工单有各自的账本。

飞书可选。配置 `feishu.profile`、`appId`、`botId`，项目资源登记真实 chat ID 并确认归属。原单渠道模式通过创建成员时填写机器人应用下的 open ID 建立身份关联。发送 `/协作 agent-id 需求`，群聊需点名机器人。已绑定成员在原话题可用 `/答 序号` 或 `/答 答复内容`。一个机器人接收入口只应由一个实例写入。

飞书私聊通知可配置 `workbenchPublicUrl`，例如 `https://collab.example.com`。团队 HTTPS 入口代理工作台页面、静态资源和工作台 API，保留该 Host。登录和操作仍由工作台核验。通知链接会打开对应项目的「待我处理」。未配置该项时，通知仅显示事项和可用的文字答复方式。执行端可继续使用 `runnerConnectUrl`，执行端审批页与独立执行 API 的代理规则见[跨主机执行端](WORKBENCH-REMOTE-RUNNER.md)。

启用 `feishu.decisionCards: true`，并为该机器人订阅 `card.action.trigger` 长连接回调。请在 `/health` 核对 `feishuCards` 的状态。卡片由 Contractor 渲染，旧卡片的点击协议继续兼容。Contractor 核对飞书账号绑定、原卡消息、群、当前待办和成果版本，再调用工作台同一套操作。卡片支持有选项的 Agent 提问、确认接单、授权本工单和验收当前版本。含受限内容的事项使用私聊或工作台，普通群卡片留在原话题。回调不可用时沿用文字通知。

有平台项目创建权限的成员可创建独立项目。项目维护人可建子项目、添加或移除成员、调整项目角色及交接管理。项目协作者可发起工单，项目只读成员可查看已授权内容。各成员可加入自己已登记的 Agent。项目、主题和工单分别保存讨论。工单讨论会进入该工单下一轮执行。已有飞书来源的公开工单可勾选「同时回复飞书原话题」。工作台所有者可在「资料与连接」绑定 `feishu.allowedGroups` 中的组并选默认主题。

启用飞书时，`GET /health` 会报告 `feishu.state` 和订阅启动次数。订阅断开时返回 503 并按间隔自动重连，收到 CLI 就绪信号后恢复 200。工单接口在重连期间仍可使用。

### 账本备份与恢复

维护期可在后端进程设置 `CONTRACTOR_PAUSE_NOTIFICATIONS=1`。文本发送、卡片新发/更新及 Octop IM 回传会保持可重试，不伪造已发送回执。`/health.notificationsPaused` 显示实际开关，`CONTRACTOR_RELEASE_ID` 可标识已核验的源码制品。暂停仅控制外发，不关闭收件或派工；做一致性备份仍需按下述方式停止写入。恢复外发需移除暂停配置并重启后端。

升级后的工作台运行一次即可建立写入锁。等执行队列和回执结清后，停止工作台和独立飞书入口，再运行以下命令。目标目录须尚未创建。

```sh
npm run ledger -- backup  /absolute/path/workbench-state /absolute/path/new-backup
npm run ledger -- restore /absolute/path/new-backup /absolute/path/restored-state
```

命令保存业务账本、当前调度器账本、已有的调度器回滚材料、飞书收件箱，以及重启所需的账号、配置和签名材料。Contractor 与 AutoLoop 各自保留调度历史，恢复前核对调度器、文件摘要和 SQLite 完整性。备份目录由当前用户独享，归档本身未加密。模型凭据、执行机配置、Git 工作区和外部资料应分别保管。恢复保留原连接配置，启动演练副本前先改为隔离端口并关闭外部监听及定时任务。

## 跨渠道测试入口

在独立测试配置增加 `"crossChannel": { "githubPollSeconds": 30 }`。登记并绑定测试群与测试仓库，运行进程使用已授权读取该仓库的 `gh`。旧飞书接入配置和测试实例的账本分开保管。跨渠道模式使用工作台验证后的绑定。

- 登录协作台，在「渠道账号」生成各自的十分钟一次性验证命令。飞书在机器人单聊发送，GitHub 用本人账号在已接入的私有仓库中新发 Issue 评论。协作台收到命令后，核对来源账号并确认。仅受理绑定生效期间发出的新命令。
- 在已接入的飞书群 @ 机器人，或在 GitHub Issue 中用新评论发送 `/协作 auto [Issue或PR完整链接] 需求`。也可填写已登记的 Agent 标识和现有工单标识。来源、回复原消息和明确引用共同核对。接续原单时保留讨论，Agent 在下一次获准运行时可读取相同项目内仍有权限的补充。
- 新话题无明确引用、来源冲突或牵头职责未确定时，进入项目维护人的待办。维护人可将一条消息记到项目或主题、挂回旧单，或另建工单。确认时重查引用，若已归入同一工单则优先续单。明确需要另开时传入 `separate: true`。选择在相关项目建单时，两边均须授权，并由目标项目维护人填写可在目标项目分享的任务说明。
- 接入采用 Super-agent 原版 Feishu／GitHub 事件转换、Engine、Store 与 AutoLoop worker。GitHub 轮询以评论 ID 关联观察到的内容修订，已编辑评论仅作为证据，无法触发委托或账号验证。仓库开启 `shareNotes` 才共享非敏感评论正文，否则保存时间和内容指纹。Figma 关联目前为资料入口。

## 飞书群消息整理

仅处理项目内已绑定且显式开启 `digest: true` 的飞书群。项目的 `discussion.agent` 选一个现有在岗 Agent，`discussion.model` 可选用已接模型，Codex 整理默认用低推理强度。`discussion.cron` 默认 `0 0,12 * * *`，即上海时间每天 00:00 和 12:00，按十二小时窗口整理。已有 `/协作` 和 `/答` 仍按即时入口处理。群整理沿用 AutoLoop 原版规则和 worker，在无候选的时段直接结束。重启后从已保存的位置继续。

- 机器人收到普通群文字时实时收集。若机器人只能收到 `@`，可设置 `discussion.history` 的 `profile`、`appId`、`userOpenId` 与 `member`，让已授权的项目维护人账号在整理时间窗内补读同一群。系统先核对当前登录身份，按原消息 ID 去重；不会把其他飞书应用里的 open ID 猜成同一个人。各群从开启时开始读取。每批最多处理 30 条候选，每条给模型最多 600 字，积压由随后窗口继续，未整理原文最多保留三天。
- `discussion.documents` 只填写项目已绑定且允许用于整理的飞书 Docx 链接。带区块锚点的链接只读该区块，每次核对读取身份及修订号。还会检索当前项目已发布的公开项目资料、已有工单、已绑定 GitHub 仓库的明确引用和最近 30 天相近的工作标题。未确认或失效的依据不能作为自动归属证据。
- 闲聊和常见凭据先在本地过滤。整理结果可以记到项目或主题，也可按已确认的引用回到原工单讨论。原工单记录该反馈，现有验收不变，Agent 在下一次获准执行时可读取这条补充。独立的新工作形成开单建议，负责人选 Agent 后才立项；只有归属或范围不明确的事项进入负责人待办。普通反馈的摘要不直接写入团队知识。
- 群中不发整理广播。项目成员可查看已归档摘要与来源；待判断和开单建议仅项目维护人可处理。联调环境的机器人订阅未收到无 `@` 的测试消息，已授权账号的按窗补读链路已经实跑。

每条原消息都有自己的来源和已观察版本。同批、同回复范围的相同文字可共同归纳。原消息撤回时删除其正文和来源关联，仍有来源的归纳继续有效。按半天补读时轮转复查每群最多 50 条已知消息，新修订通过原 ID 归入同一条记录。重新读取无法恢复两次读取之间平台未返回的中间版本。历史摘要标明所依据的修订号，已有归档的后续编辑只增加版本证据。

维护人可通过 `GET /api/discussion/<项目>/revisions/<消息ID>` 查看当前仍可核对的飞书版本。 `POST /api/discussion/<整理记录ID>/resolve` 接受可选的 `message` 字段来决定单条来源，省略时继续处理整条待确认归纳。

Super-agent 复用了原版消息归一、话题根、来源准入策略和人工确认后的建单。分批、防重复与失败后的恢复由 Contractor 按项目授权、持久入站游标和现有调度器实现。

## 派工与人工决定

- 每个项目可设置 `decisionOwner` 为接单决策人，默认取可处理任务的首位维护人。`dispatch` 的每条规则填写 `function`、`agent` 和可选的 `topic`、`decider`。自动派工依次查当前主题、父主题和项目默认规则。符合条件的牵头 Agent 唯一且在岗时自动选择。职责重叠时由维护人选择。
- 在 `GET /api/needs-you` 查看本人的接单确认、群消息建议、执行追问、资料授权、阻塞和验收。已有绑定的飞书账号收取机器人私聊。私聊带待办编号，执行决策人可回复 `/答 待办编号 序号或答复`。涉及受限资料的问题只给工单发起人，通知省略资料正文。
- 同一执行范围内的 `ask` 都是必答事项。存在未答事项时，下一轮保留在 AutoLoop 队列，补充消息、已答事项和到期复查继续合并。全部答复后才领取执行；其他工单可以继续。交接也须先答完必答事项，Agent 不能代替人结清问题。原生上下文中的未结卡片按本工单执行范围过滤。`notice` 保留原生告知语义，不参与必答检查。Contractor 的 `execution-gates.ts` 在原生 `commitLatest` 事务内用临时 View 过滤候选，再调用原版 `decide(claimNext)`，按完整队列重算原生期限；没有改写上游投影、取消等待轮或新建第二套调度器。
- `POST /api/ticket/<工单>/handoff` 接受维护人选择的在岗 `agent` 和交接 `reason`。工作台先取消排队、请 AutoLoop 停止旧进程。确认运行停止并记录证据后，调用 Super-agent 原生重派接口，同一工单和 Mandate 接续到新 Assignment。旧会话、卡片和定时回查留在旧执行范围。旧运行失联时等待回执并提醒维护人。
- 本机适配层在启动、心跳和取消时记录进程身份及观测到的后代，取消同时覆盖脱离原进程组的子进程。退出确认须等这些进程消失，信息无法核对时继续等待。记录只保留进程标识、启动时间和可执行名指纹，不保存命令参数或环境变量。
- 接替 Agent 的受限资料权限单独核对，缺少授权时旧执行保持停止、交接等待资料负责人。撤权或到期后重新申请产生新申请编号和新的负责人待办／飞书通知，同轮重复请求保持幂等。旧申请不能批准新一轮。升级前未记录读取 Agent 的历史授权保留审计，但需重新明确授权才能使用。
- 多份资料分别记录申请与批准，一份资料的申请不能代替其他资料。恢复中缺少任一份授权都继续等待；对已明确撤销的对应申请，仍需主动重申，后台不会反复自动请求。
- 每次执行记录资料所用的具体授权申请编号。撤权后即使迅速重新批准，旧回执仍按旧授权隔离。恢复复用原生停止回执与进程退出证据，保留原工单必答卡，以新资料快照和新的 CLI 会话继续；重新授权不恢复旧成果的可读性。
- 后端的研发接单、确认口径与代码交接、阻塞接续、打回修改及逐版验收见 [原工单多轮交付](WORKBENCH-ITERATIONS.md)。待验收成果的独立查阅重授权与继续执行分开记录；本轮尚未增加前端入口。

## 执行额度

定时群整理计入平台池，个人代办计入委托成员的个人池，项目工单计入所在项目的执行池。父项目和子项目分别记录。每次运行尝试只保留一笔扣账，另外按所在项目和 Agent 查看这笔用量。

项目维护人可通过 `POST /api/project/<项目>/agent-budgets/<Agent>` 设置项目内 Agent 上限，字段是 `period`（`day` 或 `month`）、`limit`（次数）及可选的 `maxMinutes`。`limit: 0` 暂停新的尝试，`limit: null` 取消这个上限。`GET /api/project/<项目>/agent-budgets` 查询本项目 Agent 的计量和配置。执行前同时核对用途池和 Agent 上限，采用更短的单次时限。原尝试的回执沿原账结算。

Agent 上限以执行尝试计数。同一个 Agent 在同一项目的整理、个人代办或工单尝试合计，同一 Agent 在其他项目单独计算。旧账仅在原执行快照能确认归属时纳入 Agent 统计。

## 模型路由

在可信的 `workbench.json` 中给 Agent 配置 `allowedModels`，把项目内不同用途的选择放在 `projects[].modelRoutes`。例如 `{"purpose":"personal","agent":"liaison","models":["gpt-6-luna","gpt-6.1-sol"]}`。`purpose` 可为 `summary`（使用项目已配置的整理 Agent）、`personal`（个人代办）或 `execution`（项目任务，包括项目咨询）。列表有顺序，每个候选均须在该 Agent 的名单中，父项目的路线不继承给子项目。已有摘要单模型覆盖 `discussion.model` 与 `summary` 路线不能同时配置。

当前路线接入本机隔离的 Codex/OpenAI。运行前先查业务额度，再在独立沙箱中用该成员的现有凭据查询 Codex 模型目录。查询不装配工单正文。只在目录确认某候选缺席时尝试下一个已授权模型。目录取不到或授权列表全部缺席时阻塞。执行一旦启动就沿用本轮模型，运行中的错误由现有的执行和重试机制处理。未配置路线的旧执行端沿用各自的固定模型。

启动前还在原额度事务重核上限。执行快照与 `GET /api/project/<项目>/usage` 的逐次回执保存路线用途、主模型、被跳过的候选、选中的模型及 CLI 实际回报。`GET /api/overview` 返回当前成员可见项目的路线。路由顺序参考 [Magpie](https://github.com/yetone/magpie/blob/main/README.zh-CN.md#路由组)。

### Token 和积分

工作台「Agent → 额度管理」支持查看积分开关、倍率、各池已用及预留，并按权限配置和调整。原有执行次数及限时配置位于同页。

- `GET /api/budget/points-status` 明确返回 `enabled`、按回执结算、超额按实记账后约束下一轮、`historicalBackcharge: false`、`hardTokenStop: false`。`points-policy` 支持管理员显式设置 `enabled`；首次未配置默认关闭，旧配置有倍率则兼容开启，已有开关不会被省略该字段的倍率更新重置。停用后新执行不预留，已预留的在途执行仍按冻结倍率结算，重新开启沿用本周期账本。
- 管理员通过 `POST /api/budget/points-policy` 设置 `tokensPerPoint`，并为每个 `provider` / `model` 配置 `multiplier` 和 `reserveTokens`。例如每 1,000 个 Token 为 1 基准积分，模型倍率为 `0.1`、`0.5`、`3`，则 10,000 个 Token 分别扣 1、5、30 积分。`GET` 同一路径读取当前配置，执行端按实际选中模型选择倍率。
- 维护人通过 `POST /api/budget/points-limit` 设置 `kind`、`subject`、`period`（`day` 或 `month`）及 `limit`。`project` 总池还约束发自该项目的整理和个人代办。`execution`、`personal`、`platform`、`agent` 可设独立额度，项目内 Agent 范围用 `项目/Agent`。平台和个人池由工作台管理员调整。周期按北京时间的派工日期归属，子项目有独立账本。
- 同一次执行的派工和积分预留共用事务。每个适用池核对余额，只记一笔逐次消耗，供不同范围查看。精确到千分之一积分并向上取整。倍率和换算率随执行冻结，重新配置影响后续执行。项目额度已用尽时，在查模型目录前挡住新任务。
- `GET /api/project/<项目>/point-budgets` 返回额度、已用、预留、余量和计入积分的 Token。`GET /api/project/<项目>/usage` 保留原始 CLI 用量和供应商费用，`pointAttempts` 补充本轮倍率、预留及扣减。未返回完整用量的尝试保留尚未核对的预留。确认未启动可释放预留。旧尝试不追扣积分，旧金额预算字段保留兼容读取。CLI 当前按回执结算，单轮用量可能超过预留。
- 每个池额外返回 `enabled`（总开关）、`enforced`（该池启用了上限）、`blocked`（本池余额已被实际用量及预留占满）、`overLimit`（实耗超上限）；单轮回执返回 `overReservation`。没有上限不代表关闭记账。启用时未配置倍率的模型不能启动，避免换模型形成漏账。
- 超预留时不截短 Token、不丢弃成果、不把多出的消耗抹为零，也不按历史新倍率重算。仍有余额时可继续；任一适用池耗尽后，换模型、换端、重复接续均不能绕过。由有权限的人补足上限或等待新周期后，显式接续原单；调高上限不会自动重跑。对于不能实时上报 Token 的 CLI，此策略不能提供单轮硬截断，预留应覆盖典型上下文与输出长度，并同时配置执行时限。

积分展示参考 [WorkBuddy 企业版积分](https://cloud.tencent.com/document/product/1831/134339)，按次预留和实耗调整参考 [New API 的倍率规则](https://github.com/QuantumNous/new-api-docs/blob/main/docs/guide/console/settings/rate-settings.md)，供应商用量与额度分层参考 [Magpie](https://github.com/yetone/magpie/blob/main/README.zh-CN.md)。

## 项目、资料与提交

- `projects[].parent` 指向上级项目，`relatedProjects` 登记有协作关系的项目。每个项目分别校验成员和资源权限。主题和子主题用于归纳多轮工作。父子工单用于拆分交付，关联工单用于连接各自独立负责和验收的工作。
- 在项目页关联飞书文档、Figma 文件或节点及其他 HTTPS 文档。Contractor 给项目来源提供稳定引用，选入工单的引用和版本进入执行记录。原链接的正文继续由源站授权。
- 仓库来源 `purpose` 为 `delivery`。`contributors` 指定可以挂交付证据的项目成员，`execution.base` 与 `execution.paths` 指定代码委托的基线和可交付路径。可用 `route: false` 在另一项目将同一仓库用作交付目标，已授权成员可用明确工单标识核对归属。
- `attribution.checkouts` 为交付仓库指定专用本地副本。可通过 `attribution.entireCommand` 增加 Entire 检查点核对。代码任务先获取远端基线，宿主保管工单 worktree，Codex 在成员隔离的文件副本中执行。停止后才核对受托差异并记录本地提交。研发通过自己有权的账号推送并关联 PR。配置与边界见 [成员执行隔离](MEMBER-EXECUTION-ISOLATION.md)。
- GitHub 的 Issue 和 PR 用仓库 ID 与各自编号定位，分支用仓库和引用名定位，再记录实际提交哈希。已关联的普通评论和 PR 状态更新只增加来源记录或更新交付。按 `base SHA + head SHA` 保留交付版本，项目成员可以回看；关 Issue 或改 PR 状态不会签署业务验收。
- 代码工单关联与验收时核对当前成果对应的运行和受托提交。PR 的仓库、head 分支、head SHA、base 分支与基线必须匹配本单执行记录。验收重新读取该 SHA 的最新必需检查，并保存检查编号和版本。默认检查为 GitHub Actions 的 `collab-pilot`，仓库可通过 `execution.requiredChecks` 配置。缺少 PR 或提交、其他工单的 PR、旧版本 CI、草稿或已关闭且未合并的 PR 均无法验收。资料整理类成果按自身成果修订验收。
- 仓库可额外配置 `execution.requiredDeployment: {"environment":"store-preview"}`。目标环境最新部署必须指向本版 PR 的 head SHA，且最新部署状态为成功。验收请求提交当前部署的 `deployment: {"id":部署编号,"statusId":状态编号}`，后端实时复查，并把部署证据写入验收历史。工作台在当前工单的「交付与验收」显示部署环境、编号和 SHA，并随验收提交后端提供的部署与状态编号。
- 交付成员首次关联 PR 后，下一版由 GitHub 轮询跟踪同一 PR 上的受托提交与对应 CI。缺证据或 CI 失败先通知本版研发，通过后通知发起人验收。研发可以拒接、退回或确认委托，负责人可在原单重新安排。后端接口见 [交付通知与研发退回](WORKBENCH-ITERATIONS.md#交付通知与研发退回)。
- Entire 安装本地 hooks，由 `checkpoint explain --json --commit` 读取检查点元数据。工作台用已登记的精确仓库、提交和执行记录归因；只有对应的 Agent 会话也被 Entire 确认时，界面才显示「会话已核对」。GitHub 的账号和记录保留原始信息，可与已验证的内部成员映射一同查看。

## 当前范围

- 工作台可创建项目、加入已有成员、挂载本人已登记的 Agent 并保存讨论。账号开通、Agent CLI、模型凭据、职责及交付仓库仍由管理员预先配置。同主机代码交付使用已隔离的 Codex + OpenAI。远程执行支持远程隔离 Codex，以及使用执行机本地 Ollama 的 Claude Code。其他 CLI 须逐一核验运行边界后启用。[跨主机执行端](WORKBENCH-REMOTE-RUNNER.md)
- 已接原版观察准入、执行规则、重试、手动停止、问题卡片、会话和定时复查。独立入口还需接通其他来源和通知插件、自动派生与分布式接续、交付发布插件和组织级费用结算。
- PR 推送与创建由研发完成。CI 验收使用项目约定的 `collab-pilot` 检查。外部资料正文在配置允许的范围内读取，GitHub 评论保留已观察的编辑版本。
- 产品端按权限隐藏来源正文和派生成果。Codex 的工作区、登录、会话、上下文与临时目录已按执行授权范围隔离，不能读取宿主 worker 历史或其他成员目录。交接时不复制旧会话。宿主私有账本仍保留审计记录，不承诺删除外部已公开代码或对宿主管理员保密。
- 本机进程跟踪覆盖已观测的进程谱系，不能提供容器或操作系统作业级隔离。首次观测前已完全脱离的守护进程不能仅靠轮询证明归属；生产执行端仍需受控的进程容器。短命令采用原生退出文件与进程组消失作为退出证据。
- 飞书 Docx 和 GitHub Markdown 可按项目接入正文，资料负责人确认后进入现行检索。验收后可核对并采用带来源版本与适用条件的结论，支持替代和失效。历史执行按原授权代次回看。配置、后端入口及真实实跑见 [资料接入与知识版本](KNOWLEDGE-VERSIONS.md)。通用模型知识提炼、组织知识图谱及轻量模型服务仍待接入。
- 每次实际执行保存 Skill、上下文与运行配置快照，读取时重新核权。模型和成员凭据必须显式配置。逐次账本保留请求模型、CLI 回报、用量与费用，缺失金额保持未知。派工检查项目与业务积分额度。历史功能核验见 [文档九点核验](PRODUCTION-CAPABILITY-AUDIT.md)。

## 运行证据

飞书卡片与项目讨论联调分别使用独立实例。三个浏览器测试账号实际创建项目、加入成员和两个 Agent，在同一主题交流并发起两张工单。后端回归验证工作台回复只返回本单原话题，消息不跨工单进入执行上下文。

飞书回调启用后，已有绑定的产品账号与新确认绑定的研发账号分别在真实测试群发起「门店推荐理由文案」与「门店推荐理由小屏换行」。两人在各自的原话题点击确认，两个受控 Agent 分别接续，研发单接续时文案单继续等待。研发点击文案验收卡被拒绝，随后各自验收两张工单。文案验收只入账一次，飞书送达的两条重复回调均被忽略，验收原卡均已结清。在原账本快照中重放文案追问和验收的真实回调，答复、验收和执行记录均未增加。

2026-11-16，用独立工作台和三个测试成员验证同一预配项目中的两张工单。产品、设计、研发分别在浏览器看到文案核对与小屏换行工单，工单动态可读，项目外账号看不到项目，直接请求工单返回 404。此轮使用受控命令执行端，覆盖项目和工单界面。项目创建、通用讨论输入与飞书原生卡片回调仍待接入，未覆盖真实多人飞书互动。

新版前端使用独立本机实例、受控命令行执行端与三种测试身份。以「门店推荐理由」验证委托草稿、资料授权、Agent 追问、原单打回至第 2 版、人工验收、知识采用与撤权。项目外的账号无法打开原单。在 390 像素宽度下检查交付页，以及返回工单列表时保留搜索条件。

2026-11-14，独立工作台通过三个分别登录的测试账号完成了门店预约提醒协作。产品账号委托设计成员的个人 Agent；设计账号授权受限资料；工程账号的正文查询、授权、答复与验收被拒；真实 Codex 经原版 AutoLoop 发出问题并用了同一会话接续。验收使用测试账号签署，系统核对已有 GitHub PR 的真实 head 和 CI，拒绝另一提交。知识采用后可检索，撤权后原工单成果及派生知识不可读，验收记录仍保留。已在浏览器检查委托入口、资料引用、撤权状态和 390 像素宽度下的页面。
