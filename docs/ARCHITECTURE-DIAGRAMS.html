SuitMe 协作台 · 系统架构图

版本口径：第四十轮（2026-11-09）· 三张图回答三个不同的问题：能做什么 / 怎么运转 / 由什么构成。

功能架构 = 能力域 业务架构 = 谁在什么时候做什么 技术架构 = 进程、模块与数据 验证：639 用例 · 40 条分层契约

一、功能架构：九个能力域

按「用户能感知到的能力」切分，不按代码目录切分。每张卡下方的共享底座是九个域共同依赖的部分。

为什么按能力域画九个域各自有明确的用户可见结果；代码目录会随重构变化，能力域相对稳定。
底座是什么九个域都读写同一份任务真源、事件主干与审计；底座不提供业务判断。
没画进来的商业化、多租户、云端部署——当前形态是本机单用户，不假装支持。

二、业务架构：一条任务穿过三种主体

横向是任务阶段，纵向是「谁在做」。同一格里如果出现两类主体，说明这一步需要人或 Agent 协作完成。

泳道怎么读从左上到右下是任务的正常生命周期；「拍板」一列可能来回多次，不是单向一次。
为什么把系统单列系统不做业务判断，但它是唯一能保证「回答被重新验证」「报告不能替代人签」的角色。
紫框那一格「确认验收」是全图唯一的高亮格——它是产品红线，也是所有自动化的终点。

三、技术架构：七层与三类外部依赖

左侧是按依赖方向排列的七层，右侧是数据落点、外部服务与验证基线。所有进程只绑 127.0.0.1。

为什么宿主层单独一层任务真源可以换（local-pg / paperclip / local），换的时候上层不改。
外部依赖的边界三个外部服务都是「不配就不用」；配置了才发请求，失败明确报错。
验证怎么读数字都能用图上的命令复跑；partial 不是失败，但也绝不写成通过。
