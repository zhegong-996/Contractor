## 0. 这份架构在回答什么

传统协作软件产品化的是**「组」**——分组、权限、项目空间、汇报关系。
AI Native 平台真正新增的价值在**「织」**——组与组、人与人之间如何自发接上。

LobeHub 把协作的时间黑洞归为三类：**执行类**（背景同步、任务说明、验收成果）、**决策类**（拍板时缺支撑材料）、**盲区类**（没人发现的兼容性 bug，到某个节点才炸）。三者都发生在**交接**上，也就是玉伯说的"织"。这份架构就是把「织」从组织默契变成可复用、可观测、可治理的产品机制。

但"织"不是无边界的网状流动：**人的职责有相对稳定的范围**，交织发生在这个范围之下与之间（第 15 节）。

还有一层此前没写透：**这套东西本身必须架在 Agent 框架上，而且必须自带知识底座**。协作过程不只是在消费知识，它在持续生产知识（决策、证据、责任链、打回原因、组织信号）；没有结构化的知识底座，「织」就只是一次次即时的消息往返，攒不下组织资产（第 17、18 节）。

## 1. 架构总览

```
入口与介入层          会话 / 画布 / Task 卡片 / 叫停 / 回滚 / 验收报告
      │
场域层                Workspace（常按业务域 / 项目开）· Task（用户可见主单元）
      │
成员与代理层          人 ↔ Personal Agent   │   岗位 Agent / 主管 Agent / Worker
      │                 职能注册表（划分可配置）· 主职能（稳定）· 领域（流动）· 邻接能力（可正式派单）
交织与执行层          @ 委派 → 反向追问 → 执行 → 风险闸门 → 证据化验收 → 核可
      │                 └ 跨职能派单 → Responsibility Transfer（默认仅本 Task）
上下文与制品层        Context Pack（投影快照）· Artifact · Skill
──────────────────────────────────────────────────────────────
知识底座 K            结构化（对象/指标/状态）· 非结构化（文档/消息/证据）· 图谱（实体与关系）
      │                 统一 ID / 统一标签 / 边级状态与证据引用
──────────────────────────────────────────────────────────────
运行时底座 J          Agent 框架：Loop / Checkpoint / 工具与 MCP / 沙箱 / Watchdog
──────────────────────────────────────────────────────────────
横切一：注意力预算    两级过滤（程序快筛 + 语义慢判）· 巡检 · 静默策略
横切二：治理平面      身份 · 数据标签 × 能力标签 · 审计 · 预算上限 · 责任链 · 授权档位策略
横切三：可观测        Trace · 成本归因 · 组织状态信号（框架原生事件流为准入底线）
```

**三条分界线**：
- 上层是流动的意图与过程，下层是持久、可验收、可追溯的对象。AI 产出绝不能只作为一条消息留在聊天流里。
- **Session 是实现细节，Task 才是用户可见单元**（DeepSeek 与 LobeHub 一致）：聊天记录会断，Task 持久化需求、执行记录、进度、评论与制品，新同事打开就能接上。
- **配置与事实的分界**：职能划分、授权档位、验证等级、汇报拓扑都是**可改的配置**；责任链、Transfer、Trace、验收记录、图谱里已验收的边是**不可改的事实**。前者调策略，后者留证据。

## 3. 核心对象模型

| 对象 | 定义 | 必备字段 |
|---|---|---|
| Workspace | 上下文与权限的边界，常按业务域 / 项目开 | 成员、数据域、共享范围、角色权限、**owner** |
| Task / Ticket | 用户可见的协作主单元 | 需求、执行记录、进度、评论、制品引用 |
| Member | 真人 | 身份、主职能（引用职能 ID）、可继承权限、成本归属 |
| Role Registry | 主职能划分的**可配置登记表** | 职能 ID、显示名、职能 owner、成员列表、版本、生效/失效时间、粒度自检结果 |
| Transfer Grant Policy | Transfer 授权档位与放宽/收紧规则的配置 | 当前档位、Task 类型白名单、次数/时间窗上限、放宽准入指标、自动收紧条件、变更审计 |
| Capability | 三层能力结构 | 主职能 / 领域上下文 / 邻接能力（各带权重与来源） |
| Responsibility Transfer | 跨职能正式派单的授权与责任转移记录 | 授权人、承接人、能力依据、授权范围（默认仅本 Task）、标准起草方、联签人、有效期、撤销条件、授权批次 ID |
| **Context Grant** | **跨 Workspace 的读授权**（D3：默认隔离，申请后授权） | 申请方、用途、**目标 Workspace owner 审批**、可见子集（片段 / 子图 / 行）、脱敏级别、只读标记、有效期、撤销条件、Trace 引用 |
| **Knowledge Node** | 知识图谱实体；三态共用一套 ID | 类型、统一 ID、标签、来源引用、状态、证据引用、版本 |
| **Knowledge Edge** | 图谱关系；**边本身带状态** | 起点/终点、关系类型、状态（草稿 / 已验收 / 可复用）、证据引用、置信度、可见性标签、有效期 |
| Context Pack | **知识底座按 Task 裁剪出的一次性投影快照**，不是知识库本身 | 引用列表（结构化行 / 文档片段 / 图谱子图）、可见性标签、版本、过期 |
| Personal Agent | 人的 1:1 信息过滤与代理面 | 绑定人、静默策略、可见范围 |
| Role Agent | 有名字/职责/记忆/工具的岗位 Agent | 岗位、专属工具、专属记忆、运行环境 |
| Trigger / Thread / Mandate | 环境事件、连续事件流、不可变授权边界 | 来源、订阅者、范围与强度 |
| Artifact | 持久交付物 | schema、版本/diff、lineage、状态 |
| Acceptance Plan | **开工前锁定**的检查项清单 | 检查项、证据类型、评分规则、锁定时间、起草方、**验证等级** |
| Evidence | 带来源的证明 | 捕获/导入的执行记录、截图、录屏、日志、commit |
| Acceptance Round | 一次验收轮次 | 逐项判定（通过/未通过/受阻）、退回原因、人核可 |
| Trace | 执行证据 | 工具调用、读写记录、模型与成本、可回放、职能快照 |
| Signal | 组织状态信号 | 指标、时间窗、阈值、预警级别（只读） |

**五条建模原则**
1. **消息 ≠ 制品**。消息是瞬时协调，制品是可寻址持久产出；混在一起就没法 diff、回放、复用、签字。
2. **权限挂在数据上，不挂在身份上**。Agent 只继承发起人的最小权限子集；跨 Workspace 默认不继承；每次读写过「能力标签 × 数据标签」双向校验。**三态知识的标签粒度不同**：结构化到行/列、非结构化到文档片段、图谱到节点与边。
3. **能力分三层，声明与派生各管一层**（主职能声明 / 领域自动派生 / 邻接能力可正式派单）。
4. **划分是配置，责任是事实**。职能表可改名、合并；历史记录里的职能是当时的快照，不回溯改写。
5. **图谱不取代原文**。从非结构化内容抽取出的关系，必须保留可回溯的原文片段引用；抽取结果本身是**推断**，默认草稿态。

**两个独立的维度，别混为一谈**：制品**状态**（草稿 / 已验收 / 可复用，管复用与回流）与验证**等级**（M9 四级阶梯，管信任强度）。

## 4. 核心机制（M1–M14）

**M1 上岗制**：每个成员产出一个供他人调用的 Agent，产品提供脚手架；Agent 状态随主人**领域**变化，主职能不变，可转归档态由他人接管。

**M2 @ 委派与反向追问**：一次 @ 生成 Delegation/Ticket，Agent 必须能在动手前反问、索取补充信息、判定"需求没想清楚"并退回。

**M3 三层能力模型与路由**：主职能（声明、稳定）→ 领域上下文（自动派生）→ 邻接能力（可正式派单）。派单规则：主职能定组 → 领域定人 → 邻接补位或正式承接。责任默认锚在主职能，跨职能承接必须走 M11。具体分几摊由 Role Registry 配置（M12）。

**M4 风险闸门分级**（按动作自动识别，不由使用者手工配置）

| 动作类型 | 默认处理 | 人出现的位置 |
|---|---|---|
| 只读检索、草稿生成 | 自动 | 不出现 |
| 常规代码、文档产出 | Agent 驱动，同行 Agent review | 抽查 |
| 数据库变更、权限变更、合并主干 | 必须真人签字 | 明确签字人 |
| 对外发布、资金、客户可见内容 | 证据化验收 + 真人核可 | 明确签字人（跨职能时联签） |
| 未分类的新动作 | 按最邻近高风险档处理 | 人工裁定后回写规则 |

**M5 按需造 Agent 与入群**：真实需求 → 造场景 Agent → 拉进当前场域 → 好用则沉淀为 Skill。

**M6 组织状态信号面 + 熔断**：只读信号、只预警不排名；一键熔断异常链路并回滚到上一个已验收 Artifact。

**M7 主动性与注意力预算**：两级过滤、周期巡检、职责边界内主动。与 P11 同源：主职能稳定，本质也是因为人的注意力与能力侧重有限。

**M8 运行时三层分离 + Watchdog**：Loop 跑云端、状态存数据库、工具在沙箱或端侧执行；起因是 Vercel 300 秒上限撑不住长程调用，LobeHub 把每步拆成单独调用、步间靠队列 + Redis 推进、工具发到 AWS 沙箱，据文章每天承受几万次执行；外部 Watchdog 查卡死与跑偏。**v0.6 补：这层由 Agent 框架承载，能力契约见第 17 节。**

**M9 证据化验收（融合 Acceptance）**
五要素：① 开工前写好并**锁定**的验收标准；② **带来源的证据**（区分捕获 / 导入与自撰，只有前两者能作数）；③ **独立评审者**（不得是产出模型，且必须支持视觉输入）；④ **逐项判定**；⑤ **人核可**。
四级阶梯：L1 自宣称 → L2 同轮复读 → L3 另一模型按标准评判 → L4 证据化 + 人核可。打回只退不通过项、冻结反馈、沉淀成下次自查标准。
**D9（v0.6）**：各 Task 类型用哪一档由 **Workspace owner** 配置（按 Task 类型 / 风险动作 / 是否对外设规则）；**系统保留不可下调的最低线**——对外发布、资金、客户可见内容强制 L4，owner 只能加严。与 Transfer 的「不可放宽护栏」同一模式。

**M10 组织自演进闭环**：Agent Vent 吐槽 → 每日聚类 → 建 Task 去修 → 次日对比（84→49）；harness 自优化（FrontierHarness 通过率 70% / 单任务成本中位数 1.68 美元，对比 Codex 66.7% / 3.47 美元、Claude Code 63.3% / 18.34 美元）。

**M11 跨职能正式派单与责任转移**
> 核心原则：**责任不随能力走，随派单动作显式转移。**

Transfer 字段：授权人（目标职能 owner / 项目主管 Agent，不能是承接人自己）、承接人（主职能 + 邻接能力 + 能力依据，不得凭自述）、**授权范围（默认仅本 Task）**、授权批次 ID、标准起草方（目标职能）、联签人与兜底责任人、有效期 / 撤销条件。

三条硬规则：① **验收标准外置**（由目标职能起草锁定，承接人不得自定）；② **主责转移 + 兜底保留**（双段责任链，高风险联签）；③ **占比可观测不禁止**（提示补人、重划职能、转岗，或提示可放宽授权档位）。

**授权档位与放宽路径**：L0 仅本 Task（默认）→ L1 同类 Task（白名单 + 次数上限 + 时间窗）→ L2 时段授权。放宽准入（默认连续 5 个 L0 达标、返工率/撤销率/越权/联签否决达标、由目标职能 owner 发起、承接人不能自提）；自动收紧（越权 / 联签否决 / P1 事故 / 主职能变更 → 回落 L0）。**不可放宽护栏**：标准外置、高风险联签、兜底责任、逐条留痕、可撤销。宽授权只免逐次人工审批，不免留痕与责任；**放宽改的是 Policy 配置，不改对象模型与责任链结构**。

**M12 职能注册表**：产品定义「怎么划分」，组织决定「划成几摊」。四条硬约束：唯一性、完备 + owner 齐备、ID 稳定（历史存职能快照、只影响未来 Task）、粒度自检只提示不拦截。变更流程：写审计 → 兼容期双写 → 重算能力地图 → 在途 Task 沿用旧职能 → 归档旧 ID。**划分可调，责任不可调。**

**M13 跨 Workspace 申请授权**（v0.6 新增，落实 D3）

> 默认**严格隔离**（读与写双向）；不是"关掉共享"，而是"共享需要一次显式、可撤销、可审计的授权"。

流程：申请（用途、范围、粒度、时效）→ **目标 Workspace owner 审批**（数据归属方，不是申请方主管，因为权限挂数据上）→ 生成 Context Grant → 生效时只开放**最小可见子集**（脱敏摘要 / 指定文档片段 / 指定图谱子图 / 指定结构化行）→ 全量写 Trace → 到期自动失效、可随时撤销。

四条规则：
1. **默认只读**，写权与跨空间回流（把 B 空间学到的写回 A）必须单独审批。
2. **授权的是子图，不是库**：靠知识底座的节点/边级标签裁剪可达性，避免整库开关导致越权半径失控（对应阻塞 B1）。
3. **授权占比进信号面，只提示不拦截**：申请一旦常态化，说明 Workspace 切错了或该合并，与跨职能派单占比同一处理。
4. **事件订阅直通不受影响**：它是同一 Thread 内的工程路由，不是跨空间读取（v0.2 已修正，别再混）。

**M14 知识库三态统一与图谱投影**（v0.6 新增，落实 P15）

> 知识库不是"给 Agent 挂个 RAG"：**协作过程本身在生产知识**——决策、Transfer、验收证据、打回原因、组织信号都入库；同时它又喂回下一次协作。

三态统一于一套 ID 与一套标签（详见第 18 节）：**结构化**（对象、状态、指标、责任链）／**非结构化**（文档、消息、会议纪要、代码、截图录屏）／**图谱**（实体关系、lineage、派生能力）。
**Context Pack 是知识底座按 Task 裁剪出的一次性投影快照**，带版本与过期；知识库是长期资产，两者不能互相替代。
**写入门槛**：图谱的边带状态（草稿 / 已验收 / 可复用）与证据引用，只有**已验收**的边能进入其他 Task 的 Context Pack 作依据；未验收的推断可见但标注「不可作依据」，防止错误沿复用链放大（对应阻塞 B3）。

## 5. 主流程：一次需求从提出到发布

1. 需求进入某 Workspace，生成 Thread 并结构化成 **Task/Ticket**，附 Mandate。
2. 人只面对一个入口（Personal Agent 或项目主管 Agent）；由它拆分、分派、跟进。
3. **按主职能定组、按领域定人**；若需引用其他 Workspace 的资料，先走 **M13 申请授权**（目标空间 owner 审批，只开最小可见子集）。
4. 若由邻接能力承接，先生成 Responsibility Transfer（M11，默认仅本 Task），并由目标职能起草验收标准。
5. 从**知识底座**裁剪 Context Pack（结构化行 + 文档片段 + 图谱子图），只纳入已验收的边。
6. 接收方 Agent 做可行性分析、反向追问若干轮。
7. **开工前锁定 Acceptance Plan**（3–5 项可观察检查项，每项注明什么算证据）；验证等级按 owner 配置的策略确定，对外类强制 L4。
8. 执行；环境事件（PR 评论、CI）由订阅直通唤醒对应 Agent。
9. 触及数据库变更等动作 → 触发 Gate，真人签字；跨职能高风险动作 → 联签。
10. Agent 在**真实产品**里逐项跑检查，采集截图 / 录屏 / 日志，生成在线验收报告。
11. 人看报告：整体通过或部分打回；打回项回到原 Agent 在保留上下文的情况下修正。
12. 核可后发 preview、合并主干、发布；全过程写 Trace；成本归集到 Task。
13. Artifact 转「已验收」，**连同证据、责任链、打回原因回流写入知识底座**（图谱边随之升为「可复用」）；Skill 沉淀。

**人在链条上出现的位置**：设目标与边界、被追问补充、跨空间授权审批、跨职能授权、高风险签字（联签）、看验收报告核可、例外介入。

## 6. 度量：两套，不混用

**内部健康度信号（只读，不做考核）**
往返轮数、追问被驳回率、闸门积压时长、返工率、调用链断裂率、跨组调用密度、可复用制品占比、验证等级分布、注意力消耗（人均被打断次数 / Agent 主动发言被采纳率）、跨职能派单占比 + 联签率 + Transfer 撤销率 + 跨职能任务返工率、宽授权覆盖率 + 自动收紧次数 + 放宽前后返工率/成本对比 + 职能划分变更次数、**跨空间授权次数 / 占比 / 平均时效 / 撤销率**、**知识复用率（Context Pack 中来自已验收知识库的比例）+ 图谱边引用错误率 + 未验收推断被误引次数**、单位任务成本 + 通过率双轴、Agent 被调用成功率。

**对外契约层**：客户/董事会要的里程碑另行维护，与内部信号物理隔离。不设 OKR ≠ 对外无承诺。

## 7. 优点

1. **协作成本从「人对人」降为「人对接口」**：异步、可并行、不占对方时间；需求在追问轮次里被澄清，返工前置消化。
2. **主职能提供稳定锚点**：路由不靠熟人默契，责任归属不靠事后追溯，同时保留领域流动的柔性。
3. **邻接能力可正式派单**：小团队不必为偶发需求专门配人；有 Transfer 记录，责任可查。
4. **人只在闸门与验收报告前出现**。文章披露：文彬三个月没在本地起过 dev，看验收报告没问题就合，开发速度至少快 3–5 倍。
5. **交接上下文不丢**：两头都是 Agent 时上下文可原封不动递过去（上游主管 Agent 给 lobe-ui 主管 Agent 提需求，次日组件加好、自动发版、回头通知升级）。
6. **验证有代价，信任才成立**：Agent 说"完成了"只花几个 token，能展示成果的报告要花几千个，但只有后者可被他人查核。
7. **组织能自己变聪明**：经验写进 Agent 的任务与标准，每日自我迭代（M10）。
8. **能力可并发复用**，产能不必按人头线性扩张。
9. **组织形态不写死**：职能划分、授权档位、验证等级、汇报拓扑都是配置；默认收窄保风险可控，放宽靠运行数据而非拍脑袋。
10. **协作即沉淀**（v0.6）：决策、证据、责任链、打回原因进知识底座并反哺下一次派单与验收；图谱让"能力地图 / 越权半径 / 制品 lineage / 证据溯源"用同一套关系算出来，而不是各建一套标签表。

## 8. 缺点与固有代价

1. **强依赖人的自觉与表达力**：Agent 质量 ≈ 主人整理自身能力的质量，天然参差，会出现"谁的 Agent 好用就被 @ 爆"。
2. **适用边界窄**：靠小团队、高信任、创始人感知力；跨时区、上百人、强合规场景下「体温」替代不了契约。
3. **抗人员流动差**：领域上下文跟着人走，人一走这部分就失效（主职能可由同组接手，领域记忆不行）。
4. **越权与成本半径同时放大**：网状调用链多轮扩散，一次授权失误影响面远大于人直接操作。
5. **对模型稳定性敏感**：追问质量一降，「织」退化成噪音；错误沿复用链放大，与焦虑传染同机制。
6. **运行时复杂度被低估**：三层分离 + 队列 + 沙箱 + Watchdog 是实打实的分布式系统工程。
7. **验收本身不免费**：文中实测直接看网页约 19 秒，看截图加两段录屏约 63 秒——**验收的价值在可查核与可交接，不在省时间**。
8. **验收标准的上限由人决定**：标准含糊就只会放过含糊成果；计划若由执行 Agent 起草，该审的是计划本身。
9. **离完全无人值守仍有工程缺口**：打回重跑按钮只复制指令需手动粘贴，回传遇权限问题需登录 CLI 补发，还多跑一轮空任务导致 3 项误报失败。
10. **主轴粒度是取舍点**：划太粗等于没划，路由仍靠默契；划太细退回岗位表，跨职能交织被扼杀。
11. **跨职能授权有摩擦成本**：Transfer、能力依据核验、外置标准、联签都会增加步骤。省掉就回到责任漂移。
12. **跨职能派单常态化会掩盖组织问题**：信号面只提示不拦截，仍需人决策。
13. **可配置 ≠ 免决策**：名单、粒度、阈值仍要人定，产品只是把代价显性化。
14. **默认 L0 会牺牲一部分效率**：稳定重复的跨职能场景每次都要一条 Transfer 和一次授权，显得啰嗦。刻意选择——先收窄建立信任基线，再靠数据放宽。
15. **配置漂移**：不同 Workspace 用不同职能表或授权档位，跨空间统计口径与联签责任会打架。
16. **默认隔离 + 申请授权会形成审批瓶颈**（v0.6）：跨空间引用都要目标空间 owner 批一次，owner 不在就卡住；授权常态化又会退化成"到处开口子"。
17. **图谱是推断产物，不是事实**（v0.6）：实体抽取会错、关系会过时；若把未验收的边当依据，错误会沿图谱放大得比聊天链更快。
18. **对框架能力的强耦合**（v0.6）：Trace 完整性、多模型评审、HITL 中断恢复都压在框架上；框架选型一旦定错，M9 / X2 / M14 都要返工。

## 9. 可能存在的问题与解决方案

| # | 问题 | 表现 | 解决方案 | 方案的代价 |
|---|---|---|---|---|
| 1 | 找不到该 @ 谁 | 规模变大后靠默契失效 | 三层路由：主职能定组 → 领域定人 → 邻接承接（M3/M11） | 跨职能多一道授权 |
| 2 | Agent 质量参差、维护断档 | 上岗制变负担，有人弃养 | 脚手架自动生成初稿；健康度可见；退役/归档/接管 | 质量可见易被当考核，须明确只读 |
| 3 | 责任真空 | 出错互相归因于"是 Agent 说的" | 责任链 + 责任锚在主职能 + 草稿态签字生效 | 留痕增加心理压力 |
| 4 | 闸门被绕过或堆死 | 全跳过，或层层审批 | 按动作自动识别风险档；低风险放行但全量可回放；超时升级 | 动作分类需持续维护 |
| 5 | 上下文污染 / 越权 | Agent 把 A 空间资料带进 B 空间 | 默认隔离 + M13 申请授权（目标空间 owner 批、最小子集、只读、有期限）；数据标签 × 能力标签双向校验 | 授权形成审批瓶颈 |
| 6 | 成本失控 | 网状调用链多轮扩散 | 每 Task 带轮数/token/时长/金额上限；超限挂起转人工；全链路归因 | 上限太紧会打断长任务 |
| 7 | 组织体温不可复制 | 创始人一不在就失灵 | 信号面 + 熔断 + 自演进闭环（M6/M10） | 设计不当会退化成变相 KPI |
| 8 | 错误沿复用链放大 | 一个错判被多条链路引用 | 制品三态 + 一键回滚 + 异常链路熔断 + **图谱边状态门槛（M14）** | 版本与 lineage 存储成本 |
| 9 | 人员流动导致领域记忆断层 | 人走，领域上下文一起失效 | Agent 与上下文解耦；留在该主职能组内、指派接管；标注"无人维护" | 接管者需领域冷启动 |
| 10 | 新人 / 新 Agent 冷启动 | 没历史上下文，问不出好问题 | Workspace 入门上下文包；新 Agent 先只读伴随 | 入门包需维护 |
| 11 | 不设 OKR 与对外承诺冲突 | 客户、董事会要里程碑 | 对外契约层独立维护、物理隔离 | 两套体系并存 |
| 12 | 效率依赖默契，难规模化 | 人数增长后噪音超过收益 | 分阶段放量；调用密度、往返轮数超阈值时提示拆分 Workspace | 拆分损失部分交织收益 |
| 13 | Agent 噪音吃光注意力 | 什么都插一嘴 | 两级过滤 + 职责边界内主动 + 巡检 + 静默策略 | 过滤太严会漏真问题，敏感度需可调 |
| 14 | Agent 掉线 / 长任务中断 | 机器重启、合盖、云函数超时 | 运行时三层分离 + 队列 + 沙箱 + Watchdog（M8） | 分布式系统复杂度 |
| 15 | 验收证据造假或标准松散 | 空口宣称、有产出无记录、事后捏造标准 | Acceptance 五要素（M9） | 消耗 token 与审阅时间 |
| 16 | 扁平直通变成越级微操 | 人越过主管直接指挥 Worker | 分层汇报；中途插手走 Task 卡片开工单 | 多一层转发 |
| 17 | 多人共用 Agent 的上下文边界 | 共享不足重复劳动，过度共享越权 | Workspace 共享 + 角色权限 + 跨 Workspace 隔离 | **行业未解**：DeepSeek 列为开放问题 |
| 18 | 主职能被领域流动冲淡 | 把"最近做支付"误当成"支付产品经理" | 主职能声明层与领域派生层物理分开；领域标签不得覆盖主职能 | 需人工维护少量主职能数据 |
| 19 | 邻接派单后责任漂移 | 开发干了产品的活，出事没人认 | M11：Transfer + 标准外置 + 主责转移/兜底保留 + 高风险联签 | 授权、核验、联签增加步骤 |
| 20 | 跨职能时标准由谁定 | 承接人用自己熟悉的标准掩盖目标职能要求 | Acceptance Plan 强制由目标职能 Role Agent 起草并锁定 | 目标职能 owner 成为瓶颈 |
| 21 | 邻接派单常态化掩盖缺人 | 某职能长期靠外职能补位，质量慢慢下滑 | 占比、返工率进信号面；只提示不拦截 | 需要人来做组织决策 |
| 22 | 职能划分变更打断历史责任链 | 改名/合并后，老 Task 查不到当年谁兜底 | 职能 ID 版本化 + 历史存职能快照 + 兼容期双写（M12） | 旧 ID 需长期保留 |
| 23 | 放宽授权后批量越权 | 一次 L2 批次授权，错判被多 Task 复用 | 逐条轻量 Transfer + 次数/时间窗上限 + 越权自动回落 L0 | 宽松期后有集中复核成本 |
| 24 | 配置漂移 | 各 Workspace 职能表/档位不一致，报表与联签口径打架 | Role Registry 与 Grant Policy 组织级唯一，Workspace 只能引用不能覆写 | 牺牲单 Workspace 灵活性 |
| **25** | **授权粒度太粗，等于整库开关** | 申请一次授权后，Agent 能读到目标空间全部资料 | 标签下沉到行级 / 片段级 / 边级；Grant 只开放指定子图与片段；脱敏摘要优先（B1） | 标签标注与维护成本，早期可先粗后细 |
| **26** | **图谱把推断当事实** | 从会议纪要抽出的关系被 Agent 当依据，错误沿图谱放大 | 边带状态 + 证据引用；只有已验收边能进 Context Pack；未验收边标注「不可作依据」；原文必须可回溯（B3） | 抽取结果需人工核可，前期图谱稀疏 |
| **27** | **owner 配置把安全底线调没了** | owner 把对外发布降到 L1，或把汇报拓扑配成无人审批 | 系统保留不可下调的最低线（对外 / 资金 / 客户可见强制 L4；高风险动作强制签字）；owner 只能加严 | 牺牲单点灵活性 |
| **28** | **框架 Trace 不完整，验收与回放失效** | 事件流缺工具调用或成本字段，Acceptance 证据链断 | 把 Trace 完整性列为框架准入硬指标；缺字段则在 J 层补齐再上 M9（B2） | 可能需要换框架或自研适配层 |

## 10. 落地节奏

- **阶段零 · 地基**：**Agent 框架选型与能力契约验收（按 Trace 完整性 / HITL / 多模型路由做准入，见第 17 节）** + 运行时三层分离（J）+ 两级过滤（I）+ 全量 Trace + **知识底座最小版（统一 ID 与标签、结构化对象、图谱节点/边带状态）**。
- **阶段一 · 最小闭环**：Role Registry（配置主职能划分）+ 领域自动派生 + @ 委派 + Task 主单元 + 消息/制品分离 + 基础闸门 + **L4 级证据化验收** + Transfer 默认 L0 + **Context Pack 从知识底座裁剪**。
- **阶段二 · 可治理**：M11 责任转移与联签、预算上限、责任链、成本归因、**M13 跨空间申请授权**、上下文隔离、打回沉淀；观察期数据达标后放宽到 L1；**非结构化片段索引与图谱抽取上线**。
- **阶段三 · 可自调节**：组织状态信号面、Agent Vent 闭环、熔断回滚、对外契约层、harness 自优化；稳定后评估 L2 时段授权与周期复盘；**图谱驱动的能力地图与影响分析**。

不建议一上来做阶段三——"体温"只有在前两层事件数据足够丰富后才有意义；同理，L1/L2 的准入指标需要 L0 跑出来的数据才可信。**知识底座不能后置**：它是 C、X1、G 的共同依赖，后置会导致三套标签体系各建一遍。

## 11. 适用边界

**适用**：小规模、高信任、高自驱、工作以知识与软件产出为主、核心成员能持续感知节奏的团队。
**不适用或需大幅改造**：强合规/强审计行业、大规模跨时区组织、以确定性 SLA 交付为主、人员流动率高的团队。应保留明确岗位责任与对外契约层，把本架构作为「织」的增强层。
**成熟度参照**（LobeHub 自动驾驶分级）：L1 问答工具 → L2 个人助手 → L3 团队成员 → L4 自治业务单元 → L5 自演进组织；文中 LobeHub 自评 L3、项目间直接提需求已有 L4 雏形。

## 15. 职能为轴，交织在轴下

### 主职能口径：按职能，还是按业务域？

| | **按职能切**（按擅长什么） | **按业务域切**（支付 / 交易 / 商家后台 / 投放） |
|---|---|---|
| 主轴回答 | 你擅长做什么 | 你负责哪块业务 |
| 分组结果 | 职能组（名单由组织配置，示例：开发 / 设计 / 产品 / 增长） | 支付域、交易域…（每域内含多种职能） |
| 一个开发既做支付又做移动端 | 始终在开发组 | 可能同时属两个域，或随项目换组 |
| 责任锚在 | **专业能力**（代码质量找开发） | **业务结果**（支付出问题找支付域） |
| Role Agent 的专属工具/记忆 | 代码库、CI、测试环境 / 设计稿、组件库、视觉规范 | 支付文档、商户数据、合规规则 |
| 好处 | 能力深度、同行评审、标准统一 | 端到端、交接少、响应快 |
| 代价 | 跨职能交接多（正是「织」要解的） | 同职能散在各域，标准易漂移；小团队一个域可能只有 1 人，没人评审 |

**结论（D4 已定）：主职能按职能切。** 理由：① "技能点主要还是在开发上面"本身就是按职能切的表述；② 业务域高频流动，不适合当稳定主轴；③ 责任锚在专业能力上更稳；④ 小团队按域切会拆散同职能导致无人评审；⑤ 按职能的代价恰好是「织」要解决的问题。
**业务域放两层**：领域上下文标签（组内精确匹配）+ Workspace / 项目容器。不放进成员层。
**什么时候反过来**：稳定的事业部制、每域有完整小分队且长期不换人。可切换配置，默认按职能。

### 划分粒度由使用者定（D11）

产品不预设「分几摊」。M12 的 Role Registry 只强制四条结构约束（唯一性、owner 齐备、ID 稳定、粒度自检），名单、命名、单列哪些职能、粒度阈值都是配置。粒度自检只提示不拦截。**架构不关心你分三摊还是八摊，只关心每一摊都有责任人、每次派单都查得到当年是谁兜底。**

### 三层能力模型与交织粒度

| 层 | 内容 | 稳定性 | 来源 | 产品作用 |
|---|---|---|---|---|
| **主职能** | 由 Role Registry 配置；唯一、稳定 | 低变化 | 声明，人工维护 | 定组、责任锚点、默认派单 |
| **领域上下文** | 当前项目、模块、业务域、近期资料 | 高变化 | 从 Task / Artifact / 图谱关系**自动派生** | 组内精确匹配、上下文包组装 |
| **邻接能力** | 开发懂一点产品、设计懂一点增长 | 中 | 派生 + 自述 | 补位、可正式派单（M11） |

- **同职能内跨领域**：自由流动，无需额外授权。
- **跨职能**：允许正式派单，但必须走 M11 显式转移责任；默认授权仅本 Task（L0）。标注「仅咨询」的轻量调用可免 Transfer。

### 由此推出的产品规则

1. **派单三段式**：主职能定组 → 领域定人 → 邻接补位或正式承接。
2. **责任锚在主职能**，跨职能通过 Transfer 形成双段责任链。
3. **与注意力预算同源**：主职能稳定，根因是人的注意力与能力侧重有限。
4. **可观测**：跨职能派单占比超阈值，既提示补人或重划职能，也提示可放宽授权档位；只提示不拦截。

## 17. 与 Agent 框架的分工边界

用户判断成立：**这不是一个纯前端 + 数据库的协作产品，它必须架在 Agent 框架上**。但边界要划清楚，否则会出现两种失败——把组织语义塞进框架（框架不认「职能」「兜底责任」），或把运行时能力重造一遍（自己写 Loop / 沙箱 / checkpoint）。

### 能力契约：框架给什么，产品自建什么

| 由 Agent 框架提供（J 层，不自研） | 为什么必须是它 | 缺失时的后果 |
|---|---|---|
| 持久执行与 checkpoint（状态、暂停、恢复、重放） | 长任务、机器重启、审批等待都靠它 | M8「持续在线」不成立 |
| **可回放的结构化事件流 / Tracing**（含工具调用、模型、token、成本） | 验收证据、成本归因、熔断回放的唯一真相源 | **M9 证据链与 X2 全部返工**（最硬的一条） |
| Human-in-the-loop 中断与恢复（interrupt / 状态编辑） | 风险闸门、验收核可、叫停 | 闸门只能做成外挂弹窗 |
| 多模型路由 + 视觉能力 | 评审者不得是产出模型；证据含截图录屏 | **L4 验收不成立** |
| 工具注册 / MCP、沙箱执行环境 | 按需造 Agent、细粒度授权 | M5、越权控制落不了地 |
| 短期工作记忆 + 跨会话长期存储 | 单次任务状态与 Agent 个人记忆 | 上下文每次从零拼 |

| 由产品层自建（框架不提供） | 为什么框架给不了 |
|---|---|
| 职能注册表、三层能力模型、owner 三级口径 | 是**组织语义**，不是运行时概念 |
| Responsibility Transfer / 双段责任链 / 授权档位策略 | 是**责任与治理**，框架只认调用关系 |
| Acceptance Plan 锁定、独立评审、逐项判定、人核可 | 框架有 eval，但没有「开工前锁标准 + 证据来源分类」这套契约 |
| **组织级知识图谱、三态统一、边级状态与可见性** | 框架的 memory / entity memory 是**单个 Agent 的记忆**，不是跨人跨空间、带责任与验收状态的组织图谱 |
| 组织状态信号面与自演进闭环 | 属于组织度量，不属于 Agent 运行时 |

> 参照：LangGraph 一类的框架把 checkpointer / Store / interrupt / tracing（LangSmith）作为一等能力；OpenAI Agents SDK、CrewAI 等也各自提供短期与长期记忆、追踪与评测，但**都没有组织级图谱**。已核实的 LobeHub 运行时与 DeepSeek harness 同样把"持续在线 + 事件路由"做在底层，组织语义在其之上。行业经验也指向同一处：**落地失败更多来自 trace 缺口，而不是模型质量**——所以框架选型要按 Trace 完整性做准入，而不是按编排好不好写。

### 三条结论

1. **选型是阶段零的阻塞项，不是后期优化**（见 B2）。评估顺序：Trace 完整性 > HITL 与恢复 > 多模型/视觉 > 持久化 > 编排表达力。
2. **知识图谱必须自建**，不要指望框架的 entity memory；后者是"某个 Agent 记住了谁"，前者是"组织里谁对什么负过责、哪份制品依据了哪条证据"。
3. **产品层与框架层之间只留一条窄接口**：结构化事件流 + 工具调用 + 中断/恢复。组织语义全部落在事件之上做解释，不渗进框架内部，换取未来可换框架。

## 18. 知识底座：结构化 / 非结构化 / 图谱

### 三态对照

| 形态 | 存什么 | 最小粒度 | 权限标签粒度 | 主要消费方 |
|---|---|---|---|---|
| **结构化** | 对象与状态：Member / Role / Task / Transfer / Gate / Acceptance Round / 成本 / 指标 | 行 / 列 | 行级、列级 | 路由、闸门、责任链、报表、信号面 |
| **非结构化** | 文档、聊天、会议纪要、代码、PR 评论、截图、录屏、日志 | 文档 + **片段**（带 offset / 时间戳） | 文档级 + 片段级 | 检索、证据、Context Pack、冷启动 |
| **图谱** | 实体关系：参与、产出、依据、授权、复用、影响 | **节点 + 边**，边带状态与证据引用 | 节点级 + **边级** | 能力地图、越权可达性、lineage、证据溯源、授权子图 |

**统一层**：三态共享一套 ID / 引用与一套标签体系（空间 × 密级 × 职能 × 时效 × 状态）。没有统一层，D3 的"授权一个子图"就只能退化成整库开关。

**Context Pack ≠ 知识库**：前者是按 Task 裁剪出的一次性投影快照，带版本与过期，用完即弃；后者是长期资产。这个区分决定了权限、过期、复用策略不会互相打架。

**图谱不取代原文**：从非结构化内容抽取的关系是**推断**，默认草稿态，必须保留可回溯的原文片段引用；抽取错误时可一键回到原文复核。

### 默认图谱本体（可直接落库，不必再讨论有哪些节点）

**节点类型**：Member、Role（职能）、Domain（领域 / 业务域）、Workspace、Task、Agent、Artifact、ContextPack、AcceptancePlan、CheckItem、Evidence、Transfer、Gate、Skill、Decision、Signal。

**五类边**：

| 类别 | 典型关系 | 用途 |
|---|---|---|
| ① 归属与职责 | Member—主职能→Role；Member—owner of→Workspace；Task—指派→Member/Agent | 路由、粒度自检、owner 定位 |
| ② 参与与派生 | Member—参与过→Task；Task—产出→Artifact；Artifact—涉及→Domain | **能力地图 / 领域派生**（不靠填表） |
| ③ 验收与证据 | Artifact—依据→ContextPack；Evidence—证明→CheckItem；CheckItem—属于→AcceptancePlan；AcceptancePlan—起草→Role | 证据溯源、标准外置核验 |
| ④ 责任链 | Transfer—授权人/承接人/联签人→Member；Transfer—范围→Task；Gate—签字→Member | 出错追责、双段责任链查询 |
| ⑤ 复用与影响 | Artifact—复用自 / 被引用于→Artifact；Skill—沉淀自→Artifact；Signal—源于→Task/Thread | **错误放大熔断**、影响分析、组织体温传染路径 |

**五类用途**：精确路由（能力地图）、越权可达性与授权子图（D3）、制品 lineage 与熔断、验收证据溯源、组织状态信号的传播路径。一套关系算五件事，是引入图谱而不是再加一张标签表的理由。

### 写入门槛与错误防线

1. 图谱边带 **状态（草稿 / 已验收 / 可复用）+ 证据引用 + 来源类型 + 置信度**。
2. 只有**已验收**的边能进入其他 Task 的 Context Pack 作依据；未验收推断可见但标注「不可作依据」。
3. Agent 产出的回流发生在主流程第 13 步，与 Artifact 转「已验收」同一事务；验收未通过不写共享层。
4. 熔断时沿 ⑤ 类边反向查影响面，回滚到上一个已验收版本（与 M6 一致）。

## 19. 阻塞性审查（v0.6）

### 已解除

D3（默认隔离 + 申请授权）、D9（owner 设验证等级）、D10（owner 设汇报拓扑）本轮拍板，均已给出机制与不可下放的底线。D4/D8/D11/D12 此前已定。

### 剩余四项：均不阻塞

D1 Workspace 切法、D2 上岗制强制与否、D5 组织体温是否产品化、D7 对外契约层是否需要——都是**可后台开关或可后置的配置**，不改变对象模型与责任链；第 12 节已各给默认值。其中 D1 之所以不阻塞，是因为 B4 建议「知识底座全局一份」，Workspace 只做容器。

### 真正的阻塞有四个（都在工程与数据层，不在组织层）

| # | 阻塞 | 为什么现在不定就开不了工 | 建议默认（不认可才需要改） | 关联 |
|---|---|---|---|---|
| **B1** | **数据标签与授权粒度** | D3 说「申请后授权」，但没定授权的最小单位，就只能整库开关，一次授权把目标空间全暴露，越权半径不可控 | 标签维度 = 空间 × 密级 × 职能 × 时效 × 状态；最小单位 = 结构化行 / 文档片段 / **图谱子图**；初期只做「只读 + 脱敏摘要 + 有效期」三件套，边级标签可后补 | M13、X1、问题 25 |
| **B2** | **Agent 框架能力契约 / 选型** | 最硬的一条。M9 的证据链、X2 的回放与成本归因、M4 的闸门中断、评审者隔离，全压在框架的事件流与 HITL 上；框架不给，这几块要推倒重做 | 阶段零按「Trace 完整性 > HITL/恢复 > 多模型+视觉 > 持久化 > 编排表达力」做准入；缺字段先在 J 层补齐再上 M9；产品与框架只留一条窄接口 | 第 17 节、问题 28 |
| **B3** | **知识库写入门槛与图谱边状态** | Agent 产出会回流进知识库；若把抽取出来的推断关系当事实，错误会沿图谱放大得比聊天链更快，且很难定位源头 | 边必带状态 + 证据引用；只已验收可进 Context Pack；未验收标注「不可作依据」；原文可回溯；与 Artifact 验收同事务写入 | M14、问题 26 |
| **B4** | **图谱全局一份 vs 每空间一份** | 决定 D3 授权、能力地图、跨空间检索能否成立。每空间一份会让「申请授权」变成跨库搬运，能力地图也碎 | **全局一份图谱 + 节点/边级可见性标签**；D3 授权 = 开放子图可达性；Workspace 只是容器，不切图谱 | 顺带把 D1 降为非阻塞 |

### 一句话结论

**组织层的决策已经全部收口**（九项已定，四项可配置默认值）；剩下卡开工的是四个工程/数据问题，其中 **B2 最硬**——它决定证据化验收能不能成立。B1/B3/B4 都围绕同一件事：**标签与状态必须细到行、片段、边，否则「默认隔离 + 申请授权」和「已验收才可复用」都只是口号**。这四个都有可直接采用的默认值，不需要再逐项拍板；按默认值进阶段零即可。
