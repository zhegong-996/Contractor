# 系统差距分析：我们要的「AI 原生协作平台」，现在差在哪

> 用户原话（愿景）：「干活通过其他 Agent，但结果在本系统 get 到；从这边派活；中间是一个决策机构；
> 沉淀整个业务的所有东西；共享一个数据/上下文底座，但不是每个人都能看到所有东西；方便 AI↔AI、人↔AI 协同；
> 关键决策点要判断；业务域之外的由其他域专业的人/Agent 判断——因为一个人注意力和判断力有上限。」
> 参照：DeepSeek Super Agent、LobeHub + Acceptance、卡兹克 Agent AutoLoop、玉伯播客。
> 结论先行：**我们的决策层骨架做得早、也做得细，但它是「单机、单人」的骨架——所有多人能力都是「为多人设计、没有一个真人验证过」。**

---

## 0. 你说的「精髓」，我理解成三句话

1. **AI 原生 = 围绕「AI 能判什么、人该判什么」重排工作流**，不是给旧工作流套一层 AI。（天猫那篇 + 玉伯的「祛魅」）
2. **沉淀不是囤积，是在「用」里长出来**——最好的知识管理是决策本身留痕，不是另建一个第二大脑。（玉伯：最好的知识管理是创作）
3. **判断是稀缺资源**——AI 的价值不在替你判断一切，而在把判断组织成「对的人 / 对的 Agent / 在对的时刻拍板」。（你原话 + Super Agent 的准入/授权）

对照这三句，我们**第 3 句做得最好（准入三档、直通、归属、验收、会签、反签都做了），第 1 句做了一半（有判定但没把「决策」做成一等公民），第 2 句做得最弱（沉淀是被动的，没把「为什么这么判」沉淀下来）。**

## 1. 你的 8 条诉求 → 现状 → 缺口

| # | 诉求 | 现状 | 缺口（诚实） |
|---|---|---|---|
| 1 | 结果在本系统 get 到 | 验收报告 / 证据 / 产物续改链 / 对账都有 | **结果回流不闭环**：执行完成不必然触发「登记产物 → 对账 → 沉淀」，大半靠人手动 `npm run artifact -- register` |
| 2 | 从这边派活 | Router 三层派活 + Agent 目录 + 用户语言解析 | **派活是「配置」不是「对话」**：非技术用户没法一句自然语言把活派出去再看到它流转 |
| 3 | 中间是决策机构 | 准入 / 直通 / 授权 / 会签 / 反签 / 验收判定**散落成 6+ 个模块** | **没有统一的「决策点」抽象**：缺一个能说清「谁有资格拍这个板、拍板前看什么、拍完沉淀成什么」的东西 |
| 4 | 沉淀一切 | 知识库 / 事件 / 记忆分层 / 审计（append-only） | 审计只记**事实**，不记**「为什么这么判」**；决策上下文没变成可复用资产 |
| 5 | 共享底座 + 分级可见 | RBAC 三档 + 知识三分区 + 读按域收窄（最扎实的一块） | **读隔离了，判断权没隔离**：一个 admin 能判所有域，和你「业务域外由别的域判」直接冲突 |
| 6 | AI↔AI、人↔AI 协同 | Agent 注册表 + delegation + HITL | AI 之间是**串行委托**，没有「多 Agent 并发 + 分歧仲裁」；AI 追人只在巡检里被动出现 |
| 7 | 关键决策点 + 跨域专业判断 | 会签 counter-sign、独立评审 reviewer、升级 escalation（只通知不代批） | **没有「域级决策委派」**：域外的事不会自动路由到对方域的 owner/Agent，只会被 admin 顺手拍掉 |
| 8 | get 到精髓 | —— | 见 §0：第 2 句「决策即沉淀」基本是空白 |

## 2. 五个结构性缺口（重点，不是「少个功能」）

### G1 决策点没有统一抽象（这是你反复在找的那个东西）

现在「决策」散在六个地方：准入（admission）、直通（pass-through）、订阅（subscription）、授权（grant-decide）、会签（counter-sign）、验收（review-readiness）。它们各自有审计，但**没有一个共同的「决策点」模型**，所以：

- 你没法回答「这个系统今天替谁做了哪些判断、还有哪些判断悬着没人拍」；
- 每个决策点的「谁有资格判」是各自写死的，不能统一改成「域外委派」。

**方案**：抽一个一等公民 `DecisionPoint`：

```ts
DecisionPoint {
  id, subject,            // 关联到任务 / 主题 / 产物
  kind,                   // admission | authorization | acceptance | countersign | cross-domain | out-of-scope
  domain,                 // 属于哪个业务域
  requiredCapability,     // 谁有资格判：domain-owner | domain-expert | independent-reviewer | human
  contextRefs,            // 判之前必须看到的：清单 + 证据 + 历史决策
  status,                 // pending | decided | delegated | rejected
  decidedBy, decidedAt, outcome, reason
}
```

把现有六个模块**注册**成 DecisionPoint，而不是重写它们。收益立竿见影：统一审计、统一「谁有资格」、统一「悬而未决」看板，以及 G3 的跨域委派有了落点。

### G2 结果回流不闭环

执行端（paperclip + Agent）跑完，结果回到系统的路径是 `delegate` + 事件，但「产物登记 → 对账 → 知识沉淀」这条链是**半自动**：

- 产物要人手动 `npm run artifact -- register`；
- 对账要人手动 `npm run reconcile`；
- 知识沉淀（wiki 投影 / L2 抽取）和「这次验收的结论」是两条独立的线。

**方案**：加一个「结果回流钩子」——执行完成（phase 变化 / 验收落库）时**自动**登记产物修订 → 巡检下一轮自动发现变化 → 提示对账 → 对账结论写进 DecisionPoint 的 contextRefs。人只做「拍板」，不做「搬运」。

### G3 跨域判断没有委派（最违背你愿景的一条）

读按域收窄做得对，但**判断权是全 admin 通吃**。你的诉求是「业务域外的由其他域专业的人/Agent 判断」——现状做不到，因为角色注册表里 role 有 owner，但**决策没有域边界**。

**方案**：给每个职能（role）加 `domain` 边界 + owner；任何跨域的 `DecisionPoint`（比如产研要改增长的业务口径）不落给发起域的 admin，而是**生成一个委派到对方域 owner / 该域专业 Agent 的决策点**，对方拍板、回执、审计。这直接复刻你说的「一个人判断力有上限」。

### G4 多人真实性是零（最大脆弱点，不是功能缺口，是地基）

主安装 `deploymentMode = local_trusted`，原生成员目录为空，`team-members.users = []`。意味着：

- 准入三档、RBAC 三档、知识三分区、域收窄、会签——**整套判定层都是为多用户设计的，但没有任何一个真实用户跑过它**；
- 现在「龚哲权限最大」不是配出来的，是**根本没有第二个用户可分配**；
- 隔离的 team-pilot（3110）用的是 `authenticated`（原生多用户），说明多用户能力是有的，只是主安装没启用。

**这是第一优先级的地基问题**：判得再准，如果现实里只有一个 `local-board`，那整套决策层就是在空转。启用多用户不是「加个功能」，是让前面所有判定第一次接触真实。

### G5 AI↔AI 是串行，不是协同

现在的协同形态：一个 Agent 领活 → 干完 → 交回 → 人/系统再委派下一个。**没有「多个 Agent 并行 + 会签 + 分歧仲裁」**。

**方案**：在 DecisionPoint 之上加「协同形态」——`countersign`（多 Agent 独立判断、一致才通过）、`parallel`（多 Agent 分头做、汇总）、`arbitrate`（分歧时交给独立评审者）。验收层已有「独立评审者」和「会签」的雏形，把它们从验收域抽象到通用决策域。

## 3. 漏洞清单（安全 / 一致性，不是功能）

| # | 漏洞 | 现状 | 建议 |
|---|---|---|---|
| V1 | 业务数据无篡改检测 | 审计 append-only，但 role-registry / org-table / knowledge 只靠 0600 文件权限 | 给关键配置加内容哈希 + 修订号校验（验收清单的 planHash 已经这么做了，推广到角色表/知识索引） |
| V2 | 执行结果可信度 | agent 声称的结果 vs 实际产出，靠证据链 + 信任 | 结果回流钩子里加「产物哈希」，验收比对时校验 |
| V3 | 域未知的 admin 全放行 | 读收窄只对 viewer 兜底拒，admin 总览可读全部 | 判断权（不是读权）要跟 G3 一起收：admin 能读，但跨域「拍板」要委派 |
| V4 | 多通道派单未定 | 主题可多群，派单仍单通道 | 见 ROUND-44-ROUTING-OPTIONS，等你选 |
| V5 | 升级只有通知、无「超时无人认领」升级 | escalation 是「只通知不代批」的静音闸 | 认领/转述若上线，要配「超时 → 升级到域 owner」 |
| V6 | 密钥与版本 | agent token 明文本机 secrets（0600）；bootstrap Node 版本只警告 | token 移到系统钥匙串；Node 声明与实际能力对齐后写死 |
| V7 | 单机系统 | 主题/产物/巡检全在 `.runtime/v06`，无多机一致性 | 这是「多人协作」与「单机工具」的本质分界：要真多人，得先有 G4 的共享底座，再谈多机 |

## 4. 优先级方案（三期）

**P0 · 地基（先做，否则上面都是空转）**
1. G4 启用真实多用户（把 team-pilot 的 authenticated 模式切到主安装，让准入/权限/域判断第一次接触真人）。
2. G1 决策点统一抽象（最小版：先把六个模块注册进 DecisionPoint，统一审计和「谁有资格」）。

**P1 · 补判定**
3. G3 域级决策委派 + 跨域路由（这是你愿景里最核心、我们最缺的一条）。
4. G2 结果回流钩子（执行完成自动登记产物 → 巡检 → 对账 → 进决策上下文）。

**P2 · 补协同**
5. G5 多 Agent 并发 + 会签 + 分歧仲裁（把验收层的独立评审抽象到通用层）。
6. 多通道派单（A 方案：显式指代优先）。

## 5. 一句实话（最重要）

你现在这套系统的**强项和软肋是同一件事**：判定层做得极细（50 条体检全绿、准入/直通/归属/验收一条不缺），
但它建在**单机、单人**的地基上。所以它现在像一个「把多人协作的规矩全都订好、却还没有第二个人进门的办公室」。

真正的第一件事**不是再加功能，是把地基从 `local_trusted` 换成真实多用户**——
否则你愿景里的「共享底座但分级可见」「跨域专业判断」这些词，在只有一个操作者的系统里，都是写在代码里、没在现实里存在过的东西。

玉伯那句话放这里最贴切：**最好的知识管理不是囤，是创作**。你的系统最该先创作的，不是更多判定规则，而是一次「两个真人 + 两个 Agent 真跑完一单」的闭环——那一单会告诉你，哪些判定是真的、哪些是自嗨。
