## 0. 这份 PRD 要解决什么

现有代码已经跑通了「飞书发起 → 人/Agent 接单 → GitHub 交付 → 发起人验收 → 知识候选」的主链路，但它产品化的主要是**审批与任务**；v0.6 架构要产品化的是**「织」**——组与组、人与人之间怎么自发接上，以及由此产生的能力、责任、证据与知识。

一句话目标：

> **把「谁擅长什么、谁为哪件事负责、AI 凭什么说做完了、这次协作沉淀成了什么」变成系统里可查、可授权、可复用的一等对象，而不是散在聊天记录和审批记录里。**

三个必须守住的立场：
1. **不推倒重来**。现有链路、真源分层、已验证流程尽量保留，新增能力以「补层」为主。
2. **不把组织写死**。职能划分、验证等级、汇报拓扑、授权档位都是配置（D3/D9/D10/D11/D12 已定）。
3. **不把验收交给模型**。授权、知识采用、最终验收始终由人决定——这条既是 v0.6 的护栏，也是本仓库 `AGENTS.md` 第 6 条红线。

## 1. 产品范围

### 1.1 目标用户与场景

小规模、高信任、以知识与软件产出为主的团队。典型场景：一个跨职能需求从 IM 发起，主职能定组、领域定人，必要时由邻接能力承接；Agent 反向追问、执行、采集证据；高风险动作真人签字；人看验收报告核可；成果与依据回流成组织知识，下次可检索复用。

### 1.2 做什么（In Scope）

- 可配置的主职能划分与三层能力模型；跨职能正式派单与责任转移。
- 默认隔离、可申请授权的跨空间上下文流转。
- 结构化 / 非结构化 / 图谱三态统一的知识底座，以及按 Task 裁剪的 Context Pack。
- 开工前锁定验收标准、独立评审、逐项判定、人核可的证据化验收。
- 风险闸门、组织状态信号、注意力预算、运行时可恢复、全量 Trace 与成本归因。
- 中文工作台，入口集中在「需要你决定」。

### 1.3 不做什么（Out of Scope，本版）

- 生产部署、全员 SSO、企业多租户、公网 Agent 服务发现。
- 无人值守的最终验收与知识采用（**仍为红线**）。**2026-11-07 修订**：原「不自动合并 / 不自动发布」已放开——本机 Git 交付在 CI 通过且审批齐全后自动 fast-forward 合并到本机 main 并自动发布本机预览制品；仍不发布业务仓库、不触发云端 CI，业务验收仍由原发起人在原会话「确认验收」。
- 自研图数据库、实体抽取器、图查询语言、Agent 记忆引擎、第二套任务调度器。
- 用「组织体温」做人员考核或排名；不设 KPI/OKR。
- 启用新模型服务、LLM 实体抽取 / embedding 语义检索（保留配置入口，等用户选定服务）。

## 2. 设计原则与不可协商红线

### 2.1 产品原则（v0.6）

| 编号 | 原则 |
|---|---|
| P1 | 传统协作软件产品化「组」，本平台产品化「织」；分组可以很粗，交织要显式的对象 |
| P2 | 消息 ≠ 制品；Session 是实现细节，Task 才是用户可见主单元 |
| P3 | 职能为轴、交织在轴下：主职能稳定、领域流动、邻接能力可正式派单 |
| P4 | 责任不随能力走，随派单动作显式转移；默认锚在主职能 |
| P5 | 权限挂数据上、不挂身份上；Agent 只继承发起人最小权限子集 |
| P6 | 划分是配置，责任是事实；历史记录存快照，不回溯改写 |
| P7 | 协作过程本身在生产知识；Context Pack 是知识底座的一次性投影快照 |
| P8 | 框架提供能力，产品提供组织语义；两者之间只留窄接口 |
| P9 | 默认收窄、按数据放宽；放宽改的是 Policy 配置，不是对象模型与责任链 |

### 2.2 工程红线（沿用本仓库 `AGENTS.md` / `PRODUCT.md`，不得因新 PRD 被冲掉）

| 编号 | 红线 | 在 v0.6 中的对应 |
|---|---|---|
| R1 | Paperclip 是唯一业务任务、成员、运行、ACL、文档修订与审计真源；SQLite 只存映射/幂等/接入状态 | 所有新对象必须标注落在哪一层（第 4 节） |
| R2 | 固定 submodule、不改上游源码；一个任务调度核心，不启动第二 hub | 新增能力走适配层或新增模块，不 fork Paperclip |
| R3 | **Agent「完成」≠ 业务验收**；`completed` 只结束本轮 | M9 人核可、Acceptance Plan 锁定 |
| R4 | 授权、知识采用、最终验收由人决定，模型不得自批 | M4 闸门、M13 owner 审批、M14 写入门槛、D9 底线 |
| R5（2026-11-07 修订） | 只用获准的测试仓库；**不发布业务仓库**；本机裸仓库的合并与本机预览制品发布已自动化（`delivery.autoMerge/autoPublish`）；本地预览标 `local-artifact-preview` | M4 高风险动作仍必须真人签字；自动合并 / 发布不改变业务验收身份 |
| R6 | 运行时状态、凭据、真实正文不提交 GitHub；测试通过不等于真实 journey 通过 | X2 Trace 与第 7 节验收口径 |
| R7 | 上游许可证与归属保留；新增依赖须写入 `THIRD_PARTY_NOTICES.md` 与 `licenses/`；非 MIT/Apache-2.0 协议先评审再引入 | 第 10 节复用矩阵、`OPEN-SOURCE-COMPLIANCE.md` |

## 3. 角色与权限

### 3.1 owner 三级口径（D3/D9/D10 用到，不能混）

| 层级 | 管什么 | 不可下放 |
|---|---|---|
| **组织级 owner** | Role Registry、Transfer Grant Policy（组织级唯一，Workspace 只能引用） | 职能 ID 稳定性、责任链不可改 |
| **Workspace owner**（数据归属方） | 验证等级策略、汇报拓扑、Workspace 切法、**跨空间授权审批** | 系统安全底线不可下调；高风险动作签字不可取消 |
| **职能 owner** | Acceptance Plan 起草、联签、兜底责任、Transfer 授权发起 | 标准不得由承接人自定 |

> 跨空间授权的审批方是**目标 Workspace owner**，不是申请方主管——这是 P5 的直接推论。

### 3.2 其他角色

- **发起人**：设目标与边界；原会话中验收、叫停、回滚。
- **承接人**：执行责任；能力依据必须来自参与过的 Task / 产出过的制品，不得凭自述。
- **独立评审者**：不得是产出模型，且必须支持视觉输入（截图 / 录屏证据）。
- **签字人**：按动作风险自动确定，不由职级决定；跨职能高风险动作需职能 owner 联签。
- **资料负责人**：对某条资料的采用与撤回负责（现有代码已有此角色，保留）。

## 4. 核心对象模型与落地层

> 「落地层」是本 PRD 相对架构草案新增的字段：写明每个对象由谁存，避免新增一套与 Paperclip 并列的业务库（R1）。

| 对象 | 定义 | 落地层 |
|---|---|---|
| Workspace | 上下文与权限边界，按项目 / 业务域开，切法由 Workspace owner 配置 | Paperclip 原生项目 + SuitMe 适配 |
| Task / Ticket | 用户可见主单元，持久化需求、执行记录、进度、评论、制品引用 | **Paperclip 原生任务（唯一真源）** |
| Member | 真人，主职能引用职能 ID | Paperclip 原生成员 / membership |
| **Role Registry** | 主职能划分的可配置登记表；ID 稳定、版本化 | SuitMe 适配层（原生私有文档） |
| **Capability** | 主职能 / 领域上下文 / 邻接能力三层 | 主职能落 Role Registry；领域与邻接由图谱派生 |
| **Responsibility Transfer** | 跨职能正式派单的授权与责任转移记录 | SuitMe 适配层（Paperclip 任务文档 + 结构化字段） |
| **Transfer Grant Policy** | 授权档位 L0/L1/L2、放宽准入、自动收紧条件 | 组织级配置，原生私有文档 |
| **Context Grant** | 默认隔离下的跨空间读授权（最小可见子集、只读、有效期、可撤销） | 复用现有 `access-contract` / 原生 grant，补 owner 与期限字段 |
| **Context Pack** | 知识底座按 Task 裁剪的一次性投影快照（引用列表 + 标签 + 版本 + 过期） | 一次性对象，引用存任务文档，不落业务库 |
| **Knowledge Node / Edge** | 图谱实体与关系；**边带状态（草稿 / 已验收 / 可复用）、证据引用、有效期、可见性标签** | Cognee / Ladybug + SuitMe 边状态适配 |
| Artifact | 持久交付物，schema / 版本 diff / lineage / 状态 | Paperclip 文档修订 + GitHub 提交证据 |
| **Acceptance Plan** | **开工前锁定**的检查项清单；含证据类型、评分规则、起草方、验证等级 | 新增，落 Paperclip 任务文档（原生修订保证不可篡改） |
| **Evidence** | 带来源的证明，区分捕获/导入与自撰 | 现有 `read_execution_evidence` + CI/截图/录屏 |
| **Acceptance Round** | 一次验收轮次，逐项判定、退回原因、人核可 | 新增，复用现有 `review` 并扩展 |
| Gate / Signal / Trace | 风险闸门、只读组织信号、可回放执行证据 | SuitMe 适配层 / `.runtime` 与结构化事件流 |
| Personal Agent / Role Agent | 人的 1:1 代理面 / 有职责记忆工具的岗位 Agent | 现有 `AgentServices` + Harness 装配 |

**两个独立维度**：制品**状态**（草稿 / 已验收 / 可复用，管复用与回流）与**验证等级**（L1–L4，管信任强度），不得合并成一个字段。

## 6. 端到端主流程（一次需求从提出到发布）

1. 飞书 / 后台进入某 Workspace → 生成 Thread，结构化成 **Task/Ticket**，附 Mandate。
2. 人只面对一个入口（Personal Agent 或项目主管 Agent）。
3. 按**主职能定组 → 领域定人**；需引用其他 Workspace 资料时先走 **FR-10 申请授权**（目标空间 owner 审批，只开最小可见子集）。
4. 邻接能力承接时生成 **Transfer（FR-11）**，默认仅本 Task；由目标职能起草验收标准。
5. 从知识底座裁剪 **Context Pack（FR-07）**，只纳入已验收的边。
6. 接收方 Agent 可行性分析、反向追问若干轮（FR-04）。
7. **开工前锁定 Acceptance Plan（FR-16）**；验证等级按 owner 策略确定，对外类强制 L4。
8. 执行；环境事件由订阅直通唤醒对应 Agent。
9. 触及数据库变更等动作 → Gate 真人签字；跨职能高风险动作 → 联签。
10. Agent 在真实产品里逐项跑检查，采集截图 / 录屏 / 日志，生成在线验收报告（FR-17~18）。
11. 人看报告：整体通过或部分打回；打回项在原上下文修正；打回原因沉淀为下次自查标准（FR-19）。
12. 核可后发 preview / 合并主干 / 发布；全过程写 Trace；成本归集到 Task（FR-27）。
13. Artifact 转「已验收」，连同证据、责任链、打回原因回流写入知识底座，图谱边升为「可复用」（FR-09/14）。

**人在链条上的位置**：设目标与边界、被追问补充、跨空间授权审批、跨职能授权、高风险签字（联签）、看验收报告核可、例外介入。

## 7. 非功能需求

| 类别 | 要求 |
|---|---|
| 权限隔离 | 授权到期/撤销后，后续执行不得再加载原资料或派生摘要；调用前后双重复查；不宣称已实现外部副本物理删除与远程缓存清理 |

## 8. 度量与验收口径

**内部健康度信号（只读，不考核）**：往返轮数、追问被驳回率、闸门积压时长、返工率、调用链断裂率、跨组调用密度、可复用制品占比、验证等级分布、注意力消耗、跨职能派单占比 + 联签率 + Transfer 撤销率、宽授权覆盖率 + 自动收紧次数、跨空间授权占比 / 平均时效 / 撤销率、知识复用率 + 图谱边引用错误率、单位任务成本 + 通过率双轴。

**对外契约层**：里程碑另行维护，与内部信号物理隔离。

**每个 FR 的验收方式**：自动测试 + 至少一条真实任务 journey（沿用现有 `SUI-xx` 编号与 `.runtime` 证据留存方式）；凡涉及权限、验收、知识采用，必须由对应真人操作，不得以模拟身份或测试通过替代。

## 10A. 渠道与界面形态绑定（2026-11-06 校准）

> 用户本轮明确：**现有「IM 会话发起 + 插件式工作台」是产品形态本身，不是待替换的临时界面**。v0.6 的对象模型必须嫁接到这个形态上，不得反过来假设一个独立 Web 入口。以下 S1–S6 与 FR 同等效力，所有功能补全均受其约束。

## 10C. 方案 C 的产品约束：可配置组织形态与自演进（2026-11-07 · 第十五轮补遗）

> 用户拍板 ② 之后追加两条产品要求：**协作部分必须可配置**，以及 **Agent 要能靠沉淀自我改进**。以下 C-P1~C-P5 与 S1–S4 同等效力，C 阶段全部实现受其约束；**不满足这些约束的「三层」不算完成**。

| # | 约束 | 可验收标准 |
|---|---|---|
| C-P1 | **组织形态可配置，层不是产品骨架** | 同一套系统支持 10 人团队全域扁平与上百人团队按业务域分层；Agent 实例与「职责绑定 / 生效范围 / 版本」分离；允许一个 Agent 兼任多个职责；禁止同一 Task 自派自验自环；配置组织级唯一、项目只能引用不能覆写；变更留快照、不回溯改写历史任务 |
| C-P2 | **职责槽位可扩展，验收是一等公民 Agent** | 配置里除 personal / supervisor / worker 外还能挂「验收 / 标准起草 / 周期巡检」等职责；验收 Agent 与产品、技术、运营的 Agent 在同一份共享现场协作（起草标准、逐项判定、部分打回、推送负责方整改）；「独立评审者 ≠ 产出模型」「不替代原发起人确认验收」两条红线不变 |
| C-P3 | **判断分三层，模型只用在必要处** | 确定性工程层（规则过滤 / 权限重评 / 注意力预算 / 周期巡检 / 清单校验）先处理且 `modelCalls=0`；AI 层只接工程层判不准的少数并记证据与成本，能本机不外部；人层保留定目标、划边界、高风险联签与最终核可；人必达消息不受任何过滤影响 |
| C-P4 | **沉淀回流，自演进按 L 级渐进不跳级** | 打回原因 → 自查标准 → 下次交付前强制先自查；异常 / 打回 → 候选改进 → 工程闸门（回放验证）+ 人审 → 版本 / 灰度 / 可回滚 → 效果对比（通过率、返工率、单任务成本、人被打断次数）；自我改进**不得自动改写**已锁定清单、权限规则、人签红线或历史任务 |
| C-P5 | **评估检查配置是否被正确执行，不逼组织长成固定层数** | `assessThreeTier()` 的 P3 / P4 改为按当前配置判定，扁平配置下不要求出现 supervisor；L1–L5 水位单独只读呈现，不与 `recommended` 混为一谈 |
| C-P6 | **循环 / 会话状态 / 执行环境三者分离，长程任务不绑机器** | 每一步（一次模型或工具调用）是一次可独立重跑的短执行单元；步号、材料、checkpoint、`modelCalls` 外置到事务库，下一棒由队列**原子激活**；同一 run 同时只有一个 ready 步；领取带 `runToken`，进程崩溃可回收且旧凭据失效；换机器只是换「执行工具的地方」，不重建会话；Agent 感知不到环境差异，但权限仍按当前身份逐步重评，已锁定清单 / 人签 / 历史任务不回溯 |

**参考来源**：赛博禅心《如何让 Super-agent 成为同事：LobeHub 的组织实验》（2026-11-01）**后半段**——Acceptance（拆检查项 → 真实产品逐项跑 → 整体通过 / 部分打回 → 每次打回沉淀成标准，下次交付前先自查）、「先通过规则过滤再交给模型判断」、Agent Vent 聚类建 Task 次日对比、L1–L5 组织自动驾驶分级、harness 自主优化后的通过率与单任务成本中位数；**同篇中间段**「如何保持 Agent 的持续在线」补充 C-P6——LobeHub 与 DeepSeek 都把 Agent 循环、会话状态、执行环境拆开，Vercel 单次 300 秒不够跑长程调用，于是「每一步（调一次模型或工具）都拆成一次单独调用，步和步之间靠队列和 Redis 推进」，工具调用发往 AWS 沙箱或用户自己的电脑，Agent 察觉不到执行环境差异，换机器只是换一个执行工具的地方。**只借产品思想**：LobeHub 主仓库 Community License 禁止复制代码；`lobehub/acceptance` 已作为 Apache-2.0 固定 submodule 引入，只作只读格式契约，见 `OPEN-SOURCE-COMPLIANCE.md`。

**已落地的地基（如实标注，不冒充已完成）**：`acceptance-plan.ts` 开工前锁定清单、`acceptance-round.ts` 逐项判定 / 部分打回 / `selfCheckStandards()`、`acceptance-report.ts` 的 `recordSelfCheck()`（幂等原子写、明确不改写已锁定清单）、`independent-review.ts` 评审者独立性、`runtime-guard.ts` 的 fast → semantic → budget 两级过滤、`runtime-bridge.ts` 的 `enforce` 与必达消息保护、B1/B2 的 `modelCalls` 记账与确定性重放；**第十六轮 C-1** 新增 `PgHostPlatform` 与 `npm run host:pg`，在本机 PostgreSQL 17 真跑事务 / 并发领取 / 步进队列 / 崩溃恢复 21/21，把「状态外置 + 下一棒原子激活」变成可验证能力。**尚未落地**：把 `src/runner.ts` / `assistant-runner.ts` 的常驻 `while` 循环切成单步执行、真实远端工具沙箱与多机切换、验收作为可配置协作 Agent、自查标准回流到交付前强制比对、候选改进的评估 / 人审 / 版本 / 灰度 / 回滚、成本与效果看板、按配置的评估口径。
